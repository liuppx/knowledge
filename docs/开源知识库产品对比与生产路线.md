# 开源知识库产品对比与生产路线

> 评估日期：2026-08-30（2026-11-07 按当前代码更新成熟度表与阻塞项）  
> 目的：判断当前 Knowledge 距离生产的差距，了解可复用的成熟开源产品，并形成后续决策依据。

> **2026-11-07 更新**：评估日之后已落地混合检索（关键词 + 单元级向量召回 + RRF + rerank，见 `knowledge/services/service_search.py`、`knowledge/services/rerank.py`）、Alembic 迁移（`migrations/versions/`）、GitHub Actions CI（`.github/workflows/ci.yml`：全量 pytest、web 构建、Weaviate 往返、非阻塞 eval 报告）、生产启动守卫（非 development 环境拒绝默认 JWT secret、`DEBUG=true`、`model_provider_mode=mock`、`warehouse_gateway_mode=mock` 和未显式设置的 token 加密密钥，见 `knowledge/core/settings.py` 的 `validate_runtime_settings`），以及 Release 热修/回滚。仍未改变的事实：默认配置仍为 `model_provider_mode=mock`、`vector_store_mode=db`；尚无真实模型（live）验收归档——现有产品验收报告在 `warehouse=mock`、`model=mock` 下运行，10/11 项通过，检索层 Q01–Q11 命中 8/11，未达 9/11 门槛。下文成熟度表与阻塞项已按此更新，其余对比与路线保留评估日原文。

## 结论先行

当前 Knowledge 不是“离生产还很远的空项目”，而是一个已经具备领域边界和控制面骨架的内测级产品：有工作区、来源资产、导入任务、解析切片、Evidence、候选知识、版本发布、授权检索、审计日志和 Agent Run，且有较多 API/服务测试。

但它还不能直接作为生产知识库交付。最主要的原因不是缺少某个 UI 页面，而是生产闭环尚未被真实基础设施和运行指标证明：默认模型是 mock、向量库默认为 DB、尚无真实模型验收归档、Warehouse 生产契约仍有 P0 阻塞项，V2 明确标注“尚未完整实现”，发布审批、冲突与过期治理、事件驱动同步和端到端运维仍不完整。

**建议定位：现在可做开发联调和受控内测；完成本文 P0 验收后，再进入单团队生产；不建议此刻直接承载高敏感、多租户或高可用场景。**

### 明确的生产阻塞项

1. Warehouse 必须提供稳定版本标识、低成本 metadata、条件/分段读取、原子幂等写入、最小权限临时凭证、统一错误码和关联 ID；详见[Warehouse 集成要求](Warehouse集成要求.md)。
2. 所有环境关闭 mock：模型网关、embedding、向量存储、对象存储和认证密钥必须是可观测、可轮换、可回滚的真实服务。启动守卫已拒绝 mock 模型/Warehouse 和默认密钥；仍需接入真实 Router、切换 Weaviate 并以 `KNOWLEDGE_EVAL_PROVIDER=live` 完成一轮检索评测和产品验收并归档。
3. 建立发布审批、发布 diff、知识冲突处理、过期/替代关系和审计留存策略（Release 回滚已实现）。
4. 对导入、检索和 Agent Run 建立质量门禁、延迟/错误率/队列深度指标和告警（检索离线评测集已建立，但尚为非阻塞报告且使用替身 provider）。
5. 完成多租户隔离、密钥管理、备份恢复、限流、灾备演练和安全测试。

### 对当前项目最有价值的借鉴

- **RAGFlow**：解析、版面、表格和引用链路；当前项目已经通过 adapter 隔离，适合继续吸收而非整个平台替换。
- **Onyx**：连接器生命周期、权限过滤、增量同步和企业搜索运营。
- **Dify/FastGPT/MaxKB**：工作流、模型配置、知识库操作和用户反馈的产品交互。
- **Outline/BookStack**：编辑、协作、权限和内容发布体验。它们不能替代当前的 Evidence/Release 模型。

不建议直接把任一产品当作“数据库/平台底座”整体搬入。当前 Knowledge 的差异化在于 Warehouse 资产控制、可审核知识生产、版本发布、服务授权和 provenance；这些正是通用问答产品通常较弱的部分。

## 建议路线

### P0：生产前门禁（必须完成）

- 真实 Warehouse 契约联调：版本、条件读、幂等上传、临时凭证、错误码、关联 ID。
- 真实模型/embedding/向量服务接入，固定模型版本和超时/重试/成本策略。
- 安全收口：生产 secret 禁止默认值；租户隔离、凭证加密轮换、最小权限、审计和限流。
- 发布治理：审批、diff、回滚、冲突标记、过期/替代关系。
- CI 与验收：运行全部 pytest；建立产品验证知识库中的 Q01-Q12 自动评测，记录召回、引用准确率、无依据回答率。
- 运维基线：备份恢复演练、SLO、队列和 Worker 指标、告警、死信和数据修复手册。

### P1：单团队生产

- Warehouse 事件驱动增量同步和断点续传。
- 混合检索（关键词 + 向量 + rerank）、权限过滤前置、中文/表格/PDF 评测集。
- 完善 Chat 追问、任务取消/重试、产物下载和知识提升体验。
- 对大文件和高并发进行容量模型与压测，明确每租户配额。

### P2：规模化与差异化

- 多租户组织/组权限、知识图谱关系、事实时效和冲突合并。
- 连接器市场与同步治理；策略化 Agent 工具和沙箱。
- 成本计量、质量反馈闭环、灰度发布和跨区域灾备。

## 选型决策

1. **继续建设当前 Knowledge**：当核心目标是“可追溯、可审核、可发布的正式知识”，且 Warehouse/Chat/Wallet 是既定生态时，这是推荐路线。
2. **组合式采用**：引入 RAGFlow parser/chunker 或 Onyx connector 思路，保留 Knowledge 的控制面和知识模型，风险最低。
3. **替换为成品**：若目标只是尽快上线内部问答，优先评估 Dify、AnythingLLM、MaxKB/FastGPT；但要接受知识版本、证据和治理能力需要补开发，且要审阅许可证。
