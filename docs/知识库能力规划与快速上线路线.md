# 知识库能力规划与快速上线路线

> 规划日期：2026-09-29
> 目标：以「带完整 UI 的独立知识产品」为形态快速上线 v1，v1 即具备混合检索与真实模型；同时守住社区赋予 Knowledge 的控制面边界。
> 配套阅读：[开源知识库产品对比与生产路线](开源知识库产品对比与生产路线.md)（成熟度与生产门禁）、[知识库架构 V1](知识库架构V1.md)、[知识库架构 V2](知识库架构V2.md)。

## 1. 定位与边界（来自社区文档）

依据 `books/yeying/夜莺社区/产品/产品组合/社区产品架构.md` 与 `产品/知识/知识产品说明.md`：

Knowledge 是**AI 工作过程的控制面 + 上下文/证据提供方**，拥有 `AgentRun`、Context、Artifact 元数据、Provenance、Evidence、Knowledge Item、Release、Grant、RetrievalLog。

它**不负责**：文件内容与对象存储权限（Warehouse）、对话交互与模型编排（Chat）、模型路由与计量（Router）、智能体进程生命周期（Agent）。

> 「独立知识产品带完整 UI」在本路线中的准确含义：把现有控制台成熟为一个可独立使用的**知识生产、检索验证、发布治理、运维**产品前端；**不**引入对话机器人、模型渠道管理或智能体进程管理界面——那些是 Chat / Router / Agent 的职责。检索台提供「查询 → 证据/引用 → provenance」的验证体验，而非多轮对话编排。

## 2. 依赖方与必须稳定的契约

许多社区应用依赖本项目，快速上线时**优先保证这些契约稳定、可版本化**：

| 消费方 | 依赖能力 | 关键接口（现有） |
| --- | --- | --- |
| Chat | 回答前取 context+证据；创建/更新/结束 AgentRun | `POST /service/search`、`/service/search/formal`、`/service/search/evidence`、`/service/runs/*` |
| Agent | 引用稳定输入资产、运行上下文、历史产物 | `/service/runs`、`/service/grants`、`/service/runs/{id}/artifacts`、manifest |
| Project | 按权限读知识库可见内容 | `/service/kbs`、`/service/releases/current` |

**契约冻结要求**：`service/*` 路由在 v1 固定请求/响应结构，纳入 OpenAPI（`docs/openapi/knowledge.openapi.yaml`），破坏性变更需版本化。这是"社区应用依赖本项目"的直接保障。

## 4. v1 交付范围（快速上线）

分两批交付，两批合起来即为「可独立使用的知识产品」；批次内可并行。

### v1.0 后端能力与契约（先决条件）

1. **退出 mock**：embedding 与生成模型经 Router 接真实服务，固定模型版本、超时、重试与成本策略。
2. **混合检索**：BM25 + 向量召回 + rerank，权限过滤前置；保留 `formal / evidence / formal-first` 三模式语义。
3. **契约冻结**：`service/*` 全量进 OpenAPI，破坏性变更版本化。
4. **安全最小收口**：生产环境启动守卫（`app_env=production` 时拒绝默认 `jwt_secret`/`debug=true`/`model_provider_mode=mock`）；对接 Warehouse scoped credential。
5. **工程基线**：引入 Alembic 迁移替换 `Base.metadata.create_all`；CI 跑全量 pytest（当前 138 通过）。

### v1.1 完整产品前端

> 状态（2026-10-01）：已落地。`web/` React SPA 覆盖下列五个工作台（另有 Warehouse / 分析运行 / 运维），旧 Jinja 控制台已删除；操作说明见[控制台操作手册](控制台操作手册.md)，开发说明见 `web/README.md`，自动化验收见[产品验证知识库](产品验证知识库.md) §7。

以现有控制台为基础，成熟为五个核心工作台：

- **知识库管理**：多知识库 CRUD、统计、成员/可见范围。
- **资产与导入**：Warehouse 浏览/绑定/上传、导入/重建/删除任务、任务状态与失败重试。
- **知识生产**：证据构建、候选审核（接受/拒绝/手工）、知识项版本与证据关联、contract/review 状态。
- **检索台**：查询 → 命中知识/证据 → 引用位置与 provenance；检索对比（Search Lab）与来源健康度。
- **发布与运维**：Release 发布/diff/回滚、ServiceGrant 授权管理、`/ops` 概览/worker/失败任务。

## 5. v1.x 增强（非上线阻塞）

按价值排序：显式知识关系边+关系图（借 Obsidian/WeKnora，补 V1 已知限制）→ MCP 工具化暴露检索/证据（供 Agent）→ 可观测/tracing 与队列看板 → 更多连接器 → 发布审批流与冲突/过期治理。

## 6. 与生产门禁的关系

本路线的 v1 面向**受控内测到单团队生产**。[开源知识库产品对比与生产路线](开源知识库产品对比与生产路线.md)中的 P0 项（真实依赖、安全收口、发布治理、评测门禁、运维基线）仍是"承载正式生产"的前提；v1.0 已覆盖其中的「退出 mock」「安全最小收口」「CI」与「离线评测集 Q01–Q12」（自动化门禁见[混合检索与真实模型落地设计](混合检索与真实模型落地设计.md) §10，`scripts/test.sh --suite eval`），其余（备份恢复演练、SLO/告警、多租户隔离）在 v1 之后按 P1 推进。

## 7. 主要风险

- **范围膨胀**：完整 UI 是最大变量。前端严格限定在上述五个工作台，任何"对话/模型渠道/智能体管理"需求都路由回 Chat/Router/Agent。
- **检索质量**：混合检索需要真实评测才能确认达标；离线评测门禁已自动化并进 CI（非阻塞报告），但离线替身 provider 不代表质量——v1.0 验收前必须以 `KNOWLEDGE_EVAL_PROVIDER=live` 对真实网关跑一轮并归档。
- **契约破坏**：`service/*` 一旦被 Chat/Agent 依赖，破坏性变更代价高；上线前必须冻结并版本化。
