# 运营本体 V1 构建风险评审

> 模式：Feature-change
>
> 日期：2026-10-24
>
> 评审对象：在 Knowledge 中新增 `DomainObject`、`Relation`、`Assertion` 和受控 `Action` 能力
>
> 前置材料：[本体论与运营知识平台调研](本体论与运营知识平台调研.md)

## 1. 结论

**Validate first。** 方向与 Knowledge 的 Evidence、Release、Grant、AgentRun 边界一致，但当前没有真实使用记录证明“关系查询和时态事实”已经成为用户完成核心工作的阻塞项。先用一个真实的“合同—产品—组织”样本做人工服务验证，再决定是否进入数据库、API 和前端实现。

这里区分两个判断：

- 技术上可以构建轻量运营本体。
- 产品上尚未证明需要立即构建通用本体平台。

## 2. 最大风险

- **R1 `feature-fit`：** 在没有真实决策问题和重复工作流证据的情况下先设计通用对象、关系和断言模型，最终可能得到结构完整但无人持续维护、检索收益也不明显的“知识图谱功能”。
- R2 `trust`：合同、客户和员工事实涉及来源权威性、时效、PII 和访问控制；如果用户不信任事实合并与权限边界，就不会让 Agent 依赖这些数据执行动作。
- R3 `positioning`：如果 V1 同时覆盖合同、产品、客户、员工、MDM、规则推理和动作运行时，Knowledge 会从“证据优先的知识控制面”膨胀成边界不清的企业数据平台。

## 3. 需求等级

**L1 - one ask。** 已有一次明确的产品方向请求，并且当前架构文档把“显式知识关系边”列为增强项；但尚无重复用户请求、人工维护的替代流程、失败检索记录、业务任务受阻或付费/留存证据。

达到以下任一条件后，可以升级到 L3：

1. 同一目标用户在实际工作中反复提出当前 RAG 无法稳定回答的关系、时间或冲突事实问题。
2. Chat、Agent 或 Project 的核心流程因为缺少对象身份、关系过滤或事实有效期而不能完成。
3. 知识运营人员已经在表格、脚本或人工清单中持续维护这些关系，形成明确替代工作流。

## 4. 证据台账

| 信号 | 强度 | 说明 |
| --- | --- | --- |
| 产品负责人明确认可 `KnowledgeItem / DomainObject / Relation / Assertion` 的区分，并要求调研相似产品 | weak | 证明方向受到关注，但只有一次请求，不证明会改变使用行为 |
| V1 文档明确记录“缺少显式知识关系边、冲突合并和事实过期判定” | weak | 证明能力缺口存在，不证明缺口已阻塞真实用户 |
| 能力规划将“显式知识关系边+关系图”列为 v1.x 增强项 | weak | 证明内部路线一致，不等同于用户需求证据 |
| Palantir、Wikibase、Stardog、MDM 等产品在对象、关系、事实和治理上已有成熟实践 | medium | 证明问题类别真实且可解，不证明 Knowledge 的目标用户现在需要同样深度 |
| 当前评测集主要验证文档定位与检索，没有合同适用范围、组织关系、有效期或冲突事实题目 | counter-signal | 当前验收体系无法证明新增本体层带来可测价值 |
| 仓库中尚未发现真实合同、产品、客户或员工样本及持续维护关系的操作记录 | counter-signal | 缺少能够指导对象身份、权限和关系基数设计的真实数据 |

## 5. 无代码验证计划

### 5.1 样本边界

只选择一个真实或完成脱敏的“合同—产品—组织”知识库，不接员工数据。样本最低包含：

- 5 份合同或合同修订版本；
- 5 个产品；
- 3 个组织；
- 至少 2 个地区或适用范围；
- 至少 1 组时间变更；
- 至少 1 组互相冲突或来源优先级不同的事实。

如果拿不到这些真实或脱敏材料，不进入实现设计，因为表结构会建立在想象数据上。

### 5.2 人工事实表

先用表格或 JSON 文件人工维护，不新增数据库表。每条记录至少包含：

```text
subject_type
subject_external_id
predicate
object_type_or_value
object_external_id_or_value
valid_from
valid_to
observed_at
status
confidence
evidence_unit_id / source locator
reviewed_by
```

对象只保留业务稳定标识与外部系统映射；不要在验证阶段设计通用属性系统、规则语言、RDF/OWL 兼容或图数据库投影。

### 5.3 决策问题集

准备 10 个问题，其中至少 5 个必须要求关系、有效期或冲突裁决，不能仅靠相似文本召回稳定回答。例如：

1. 当前在中国区适用于产品 P7 的有效合同是哪一份？
2. 合同 C123 覆盖哪些产品和地区？
3. 某合同修订生效后，哪些旧断言应变为失效或待复核？
4. 同一产品出现两个相互冲突的适用合同，系统应展示哪些证据和裁决状态？
5. 组织 O1 名称变化后，历史合同关系是否仍能解析到同一个对象？
6. 哪些结论只有候选证据、尚未被正式发布？
7. 固定到旧 Release 的服务应看到哪个时间点的事实？
8. 当前 Release 中哪些事实引用了已缺失或已变化的 SourceAsset？
9. 哪些产品没有任何当前有效合同？
10. Agent 在执行动作前需要展示哪些事实、证据和授权信息？

同时保留 5 个普通文本检索控制问题，用于判断收益是否来自结构化关系，而不是样本内容本身更容易。

### 5.4 人工交付方式

由一名知识运营人员根据人工事实表和现有 Evidence 手动回答问题；另一名业务使用者或消费方负责人只看最终答案、关系路径和引用，不接触事实表。记录：

- 是否得到唯一或明确分歧的答案；
- 是否展示有效期和当前状态；
- 是否能回到 Evidence 原文；
- 是否暴露冲突而不是静默覆盖；
- 回答耗时；
- 使用者是否会据此作出下一步判断或动作。

### 5.5 预先确定的通过标准

只有同时满足以下条件，才把结论升级为 **Build small**：

1. 10 个决策问题中至少 8 个能得到可核验答案，并且每个答案都能回到 Evidence。
2. 至少 3 个问题被确认无法由当前纯文本检索稳定解决，而对象/关系/有效期明确消除了歧义。
3. 至少出现 1 个真实冲突或事实变更场景，证明 `valid_from / valid_to / status / evidence` 不是预留字段。
4. 业务使用者确认其中至少 1 个答案会影响实际判断、审批、检索范围或 Agent 动作。
5. 知识运营人员能够解释对象合并、冲突保留和发布边界；若只能由开发者维护，则验证失败。

出现以下任一情况，则维持 **Don't build yet**：

- 主要问题使用现有 Evidence + 混合检索已经能稳定回答；
- 无法取得真实或脱敏样本；
- 对象 ID、权威来源或访问边界无法确定；
- 所有关系都只被使用一次，没有持续维护价值；
- 使用者只需要关系图展示，不需要关系过滤、时态判断或受控动作。

## 6. 可检验假设与实验

当前环境未提供 `define-hypothesis` 和 `measure-experiment-design` 技能，因此在此内联最小可执行版本。

**假设：** 我们相信，为需要判断合同适用范围的 Knowledge 使用者提供“带 Evidence 和有效期的合同—产品—组织关系”，会让他们能够回答纯文本检索无法稳定回答的当前有效合同问题；衡量方式是在 10 个预设决策问题中至少 8 个答案可核验，且至少 3 个问题明确依赖关系或时态过滤。

实验摘要：

- **唯一决策指标：** 可核验决策问题通过数，同时记录其中真正依赖关系/时态过滤的问题数。
- **样本与周期：** 一个真实或脱敏知识库、10 个决策问题、至少一名运营人员和一名消费方负责人；在一次完整人工演练中完成。
- **胜负规则：** 满足 5.5 的全部条件则进入窄范围 V1；任何硬条件失败都不开始通用本体实现，先修正场景、身份或证据边界。

## 7. 后续路由

下一步应路由到 `define-hypothesis`，再进入 `measure-experiment-design`；当前环境没有这两个技能，因此已在第 6 节提供最小替代物。

验证通过后，再进入问题定义和 V1 需求设计，范围只包括：

- 合同、产品、组织三个对象类型；
- 稳定对象 ID 和外部标识映射；
- 有方向、两端类型受限的关系；
- 带有效期、状态和 Evidence 的事实；
- 冲突并存与人工裁决；
- Release 快照和 Grant 读取边界；
- 结构化过滤与现有检索组合。

在验证通过前，明确不进入数据库迁移、OpenAPI、前端关系图、规则引擎、图数据库、员工 PII、自动 Agent Action 或通用本体编辑器设计。
