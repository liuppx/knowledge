# 运营本体 V1 公开数据代理验证

> 状态：公开数据完整性检查、Knowledge 技术代理 pilot、实体解析压力测试和采购标识覆盖研究已执行；正式真实工作流验证尚未执行。
>
> 执行日期：2026-10-25。
>
> 对应研究协议：[运营本体 V1 实证研究方案](运营本体V1实证研究方案.md)。

## 1. 结论

可以使用公开数据继续验证，而且不需要先虚构企业内部数据。公开来源已经足以构造一套可复现的技术代理研究，用来检验：

- 合同结论是否能回到原始 Evidence span；
- `Entailment / Contradiction / NotMentioned` 是否被明确区分；
- 合同/采购对象是否具有稳定外部 ID；
- 修改、有效期和历史版本是否需要一等时态模型；
- 合同、产品/服务品类、买方和供应商是否可以形成可核验关系；
- 法人当前名称、历史名称和登记机关 ID 是否能够支持对象身份解析。

但公开数据不能替代全部真实验证。它不能证明 Knowledge 已有真实付费需求，不能测出你的组织维护本体的实际成本，也不能验证生产环境中的 Grant 泄漏风险。因此当前结论是：

> **Don't build yet：公开代理 pilot 发现了受限检索窗口下的多记录聚合问题，但在同对象族检索窗口扩大到 15 条后，Evidence 完整性差异消失；不建立通用 assertion 投影的来源原生工具 C3 在实际答案、证据和拒答上与 E 持平；透明的确定性 planner 也通过了实现前冻结的 30 条 test challenge。GLEIF 金标进一步证明名称相似度不能安全合并实体；采购标识研究则把“来源内配对”“权威 namespace”和“全球 ID 映射”分开：TED XML 将 winner 配对恢复到 13/13，Registry Agency 又把 7/7 个 XML CompanyID 确认到 `RA000065`，但这些 `RA000065 + UIC` 在 GLEIF 中仍没有权威 LEI 命中，29 个组织的权威 LEI 自动映射继续为 0。现有证据支持来源适配器、权威 crosswalk 和人工复核，不足以证明必须建设通用运营本体。**

## 2. 为什么选这五个来源

本次没有追求更多数据集，而是选择能够组成证据链的最小来源组合：

```text
原始合同 + 独立人工标注
  ContractNLI / CUAD
        ↓
合同—产品品类—组织—修改交易
  USAspending / TED
        ↓
组织稳定身份、历史名称、登记机关 crosswalk
  GLEIF
```

| 来源 | 最原始素材 | 独立金标或客观约束 | 主要验证对象 | 不能证明什么 |
| --- | --- | --- | --- | --- |
| ContractNLI | 607 份 NDA 原文，含 SEC 文件和公开 PDF | 17 个固定命题、三分类结论、人工 Evidence span | Evidence、否定、未知、冲突语义 | 多合同替代、产品主数据、业务价值 |
| CUAD | 510 份商业合同全文 | 律师监督下的 41 类条款与原文 offset | 当事方、签署/生效/到期/续期、条款 Evidence | 跨系统实体合并、权限 |
| USAspending | 美国政府 Award 与 transaction 原始公开记录 | Award ID、PIID、UEI、修改号、金额守恒、PSC/NAICS | 合同—组织—品类、修改时间线、金额重放 | 签署合同全文、内部审批 |
| TED | 欧盟官方采购通知和修改通知 | notice ID、previous notice、组织 ID、CPV、发布日期 | 通知版本链、多供应商、品类和组织关系 | 私有合同条款、企业内部授权 |
| GLEIF | 全球 LEI 参考记录 | LEI、登记机关 ID、当前/历史法定名称 | 对象身份、别名、更名、crosswalk | 所有非 LEI 组织的完整身份金标 |

选择原则是“一手记录 + 外部可核验约束”。ContractNLI/CUAD 的标签不是原始业务记录，但它们与原文同时提供，可作为独立于本项目的人工金标；USAspending、TED 和 GLEIF 则是官方记录本身。

## 5. 已执行的 Knowledge 技术代理 pilot

本轮没有实现本体数据库。它使用 Knowledge 真实的 `ServiceSearchService._search_evidence` 路径，与内存中由同一批官方记录程序化派生的事实视图做上限对比。

冻结的实验输入为：

- 10 个 USAspending Award family；
- 10 条 TED 修改通知链；
- 5 个含历史法定名称的 GLEIF 实体；
- 129 条 Evidence record、221 条结构化 assertion；
- 50 个问题：35 个关系/时态题、10 个普通文本控制题、5 个无答案题；
- 归一化一手数据 SHA-256：`78bb51d6764f6988e2ee2c12f10504cbeafa1d8f1085bfb26d85012e0ef366f0`。

实验组：

| 组 | 实际处理 | 用途 |
| --- | --- | --- |
| A | 全局词法检索 | 最低检索基线 |
| B | 全局混合检索 + rerank | 当前检索路径的离线替身 |
| C | 按 USAspending/TED/GLEIF 来源过滤后混合检索 | 检查粗粒度 metadata filter |
| C2 | 按 Award/notice-chain/LEI family 过滤后混合检索 | 首轮后加入的保守、事后稳健性上限 |
| C3 | 直接查询归一化的 USAspending/TED/GLEIF 来源记录，并执行 6 个窄的确定性工具 | 检查是否能不建立通用 `DomainObject/Assertion` 投影就完成当前任务 |
| D | 内存结构化事实查询 | 验证对象/时态/聚合语义 |
| E | D + 必需 Evidence key | 验证正确性和可追溯性 |
| F | 未执行 | 本地没有 live 生成/rerank gateway，不用离线替身冒充正式结果 |

这里 A–C2 的“正确”是 **oracle Evidence completeness**：只检查生成正确答案所需的记录是否全部进入检索结果，假定下游生成器完美。它是对文本检索有利的上限，不是实际答案正确率。C3、D 和 E 则要求答案与官方记录派生的 gold 完全一致。C3 与 D/E 共用 oracle operation 和稳定 ID 参数；它只用于比较数据建模的必要性，不验证自然语言规划或实体解析。

### 5.1 基线结果（`top_k=6`）

| 组 | 关系/时态题 | Evidence recall | 普通文本控制题 |
| --- | ---: | ---: | ---: |
| A | 48.6% | 76.5% | 100.0% |
| B | 51.4% | 69.3% | 90.0% |
| C | 51.4% | 69.3% | 80.0% |
| C2 | 57.1% | 82.9% | 100.0% |
| C3 | 100.0% exact | 100.0% traceable | 100.0% exact |
| D | 100.0% exact | n/a | 100.0% exact |
| E | 100.0% exact | 100.0% traceable | 100.0% exact |

在这一个执行基线上，E 相对 C2 提高 42.9 个百分点，bootstrap 95% CI 为 25.7%–60.0%，McNemar exact 双侧 `p=0.000061`。它通过了研究协议中预先冻结的“提高至少 10 个百分点且区间不跨 0”效应门槛。但 `top_k=6` 和 C2 本身不是预注册实验条件，不能把这一行结果单独当成建设依据。

### 5.2 错误分类

C2 的 15 个失败全部来自 USAspending：

- 8 个问题要求对 7–14 条 transaction 求当前累计 obligation；
- 7 个问题要求按 `as_of` 截断后对 4–8 条 transaction 求和；
- TED 修改链 10/10 完整命中；
- GLEIF 历史名称身份解析 5/5 完整命中。

因此，基线增益并不是多个关系/时态机制的广泛证据；它集中在一个具体问题：当求和所需的记录数超过检索窗口时，纯文本检索无法收齐全部 Evidence。

| ---: | ---: | ---: | ---: | ---: |
| 6 | 57.1% | 82.9% | 42.9% | 25.7%–60.0% |
| 10 | 85.7% | 97.6% | 14.3% | 2.9%–25.7% |

C2 和这个敏感性检查是看过首轮结果后加入的事后稳健性分析，不是预注册实验组。它的作用不是提高置信度，而是尝试推翻基线结论。结果确实推翻了“公开样本已证明必须建设本体”的说法：同族检索窗口达到 15 后，文本检索的 Evidence 完整性上限与 E 持平。

### 5.4 更小架构替代方案 C3

C3 不建立 221 条通用 assertion，而是直接使用归一化的来源记录，分别实现：

- USAspending 全量 transaction 求和；
- USAspending `as_of` 截断求和；
- TED 前后通知链、共同 buyer ID 和 CPV；
- GLEIF 历史法定名称解析；
- USAspending 产品描述和 TED 标题读取。

C3 在 50 个问题上得到：

| 指标 | C3 | E |
| --- | ---: | ---: |
| 全部问题 exact accuracy | 100.0% | 100.0% |
| 关系/时态题 Evidence traceability | 100.0% | 100.0% |
| 普通文本题 accuracy | 100.0% | 100.0% |
| 无答案拒答 | 100.0% | 100.0% |

因此，当前问题集已经提供一个具体的更小替代方案：在意图和稳定 ID 已知的前提下，来源原生记录和窄工具已能完成全部样本任务。这不证明 C3 可以取代真实产品中的本体，但它使“必须先建通用本体”成为一个已被当前证据否定的主张。

### 5.5 冻结的自然语言 planner challenge

为了取消 C3 “直接收到 operation 和参数”的 oracle 优势，先单独冻结了 [`planner_challenge_v1.json`](validation/ontology-v1/public-study/planner_challenge_v1.json)，再实现 planner。挑战集 SHA-256 为 `b87251e223472c1f69fd15fa9128c437a700338ad5f0bf5274d8f0ea09032cc1`，包含：

- 12 条 development case；
- 30 条 test case，其中 23 条可回答、7 条必须拒答；
- 6 个 C3 operation；
- 不存在 ID、近似 ID、一对多供应商名称、超出工具能力和显式否定表达。

实现前已冻结工具选择、参数、拒答、false merge、端到端答案和 Evidence 门槛。planner 运行时只接收 query 和官方来源记录，不读取 case ID 或预期标签。它使用精确 PIID/Award ID、TED publication number/UUID、GLEIF 历史名称匹配，并对一对多或近似字符串拒绝自动合并。

首次执行在 T17 失败：“给我标题，不需要版本链”中被否定的“版本链”被误当成 `ted_chain`。修复通用的否定作用域规则后重跑；期间没有修改题目、标签、hash 或门槛。

test split 结果：

| 指标 | 结果 | 冻结门槛 |
| --- | ---: | ---: |
| operation accuracy | 100.0% | ≥ 95% |
| exact parameter match | 100.0% | ≥ 90% |
| USAspending/TED/GLEIF 分来源参数正确率 | 100.0% / 100.0% / 100.0% | 各自 ≥ 80% |
| 负例 abstention | 100.0% | 100% |
| false merge | 0 | 0 |
| planner + C3 端到端答案 | 100.0% | ≥ 90% |
| Evidence traceability | 100.0% | 100% |

这进一步说明：对当前受控的问法和稳定官方 ID，透明规则已足以驱动 C3，没有必要为此引入本体或 LLM planner。但该 challenge 已提交到仓库，实现者可见，而且问题是基于公开记录人工编写的，不是外部保管的隐藏集或真实用户 query log。

### 5.6 GLEIF 实体解析金标与阈值反证

为了单独验证 H4，从 GLEIF 官方记录冻结了 [`entity_resolution_pairs_v1.json`](validation/ontology-v1/public-study/entity_resolution_pairs_v1.json)：

- 7 个正例：当前法定名称与同一 LEI 下的官方历史名称；
- 15 个 hard negative：全文搜索得到的相似名称，但是不同已发行 LEI；
- 20 个唯一 LEI；
- pair 文件 SHA-256：`0d1f07953ffa1474365e4ec3365512908534cf02a64781a617f6195dfa9d7d9d`；
- 归一化 GLEIF 源 SHA-256：`a93e030095ca674431833783aa6cdbb0f85902a50ddfa24d85fad7ab7f67e7e9`。

正负标签来自官方 LEI，而不是本项目对名称的主观判断。对三种常见名称策略扫描 `0.00–1.00` 的全部阈值：

| 方法 | 最佳 F1 | precision | recall | false merge | 存在通过 H4 的阈值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 归一化完整字符串 SequenceMatcher | 66.7% | 54.5% | 85.7% | 33.3% | 否 |
| 去法律后缀 token Jaccard | 48.3% | 31.8% | 100.0% | 100.0% | 否 |
| 两者取最大分 | 63.2% | 50.0% | 85.7% | 40.0% | 否 |
| 权威 alias→LEI crosswalk | 100.0% | 100.0% | 100.0% | 0.0% | 是 |

不存在一个名称阈值能同时达到 H4 的 `precision >= 98%`、`recall >= 90%`、`false merge <= 1%`。原因不是调参不够，而是排序本身出现反转：

- `HP INC.` 与同一实体的 `Hewlett-Packard Company` 字符串分数约为 0.276；
- `SILVER X MINING CORP.` 与不同 LEI 的 `Silver Bow Mining Corp.` 分数约为 0.905。

因此，高分可能是不同法律实体，低分反而可能是官方更名。当前客观结论是：

> 对象身份需要稳定外部 ID、权威别名 crosswalk 和未解析项的人工复核；不应用名称相似度静默自动合并。

这证明了身份治理机制的必要性，但仍不证明需要通用本体平台：当前样本上，来源适配器维护的 alias→LEI 映射已经达到 H4 上限。hard negative 是主动选取的压力样本，不能用于估计真实业务中的近似名称比例。

### 5.7 采购稳定 ID 覆盖与跨来源映射

名称阈值反证回答的是“不能怎样合并”，本轮进一步测量官方采购记录实际提供了多少可用稳定 ID，以及这些 ID 能否直接映射到 GLEIF。研究对象仍是同一批冻结记录：10 个 USAspending Award family 和 10 条 TED 修改链，共得到 29 个唯一来源组织：6 个 USA recipient、10 个 TED buyer、13 个 TED winner。

来源内结果：

| 指标 | 结果 | 能证明什么 |
| --- | ---: | --- |
| USAspending Award 含 UEI | 10/10，100% | 当前样本可使用 UEI 作为 USAspending 来源内 recipient key |
| USA 同名映射到多个 UEI | 0 | 当前小样本未观察到同名冲突，不代表总体不存在 |
| USA 同 UEI 映射到多个名称 | 0 | 当前小样本未观察到名称变化，不代表 UEI 可替代历史名称表 |
| TED buyer 名称—标识配对 | 20/20，100% | 20 份前后通知的 buyer 原始行均可配对 |
| TED buyer ID 跨修改链稳定 | 10/10，100% | buyer ID 可支持本样本的通知链内关联 |
| TED winner 搜索字段可验证配对 | 7/13，53.8% | 5/6 份含 winner 的通知可从原始重复行完成配对 |
| TED winner XML 补证 | 6/6 | 问题通知的显式 Organization/Tenderer 引用恢复全部配对 |
| TED winner 最终来源内配对 | 13/13，100% | 搜索原始行与官方 XML 合并后的来源内结果 |
| XML CompanyID 声明 scheme | 0/7，0% | 1 个 buyer 和 6 个 winner 都只有 CompanyID 值与国家代码 |

TED 搜索字段的 53.8% 不是“标识字段缺失率”。问题通知同时发布了名称和标识，但搜索 API 将它们扁平化为长度不等的数组。实现仍然只有在单语言原始名称行与标识行等长时才按位置配对，并且在配对后才去重；否则转向官方 eForms XML。XML 中 6 个 winner 分别通过 `TenderingParty/Tenderer` 引用到独立 Organization，再从同一 Organization 读取 `PartyName + CompanyID + Country`，因此可恢复：

- `МЕТАЛИК АД → 833067427`；
- `ВАЛИС ООД → 123630361`；
- `ПЕТКО ПЕТКОВ - 24 ООД → 123587426`；
- `ЕЛИТ - МОНТАЖ ЕООД → 123018503`；
- `МЕТАЛИНВЕСТ-РЕМКО ЕООД → 106567752`；
- `РУДИН ООД → 202714798`。

XML 解决了“谁对应哪个 ID”，没有解决“这个 ID 属于哪个权威 namespace”。7 个目标 Organization 的 `CompanyID` 元素都没有 `schemeID`、`schemeName` 或等价登记机关属性，只有国家代码 `BGR`。GLEIF 官方 Registration Authority 列表中，保加利亚同时存在：

- `RA000065` Commercial Register；
- `RA000066` Public register and filing cabinet；
- `RA000730` Bulstat Registry；
- `RA000731` Register of non-profit legal entities for public benefit。

仅从企业名称和编号形态推测 Commercial Register 不足以自动合并，因此进一步调用保加利亚 Registry Agency 的公开商业登记接口 `/CR/api/Deeds/{UIC}`。7 个目标 UIC 全部得到精确记录，返回 UIC 与 TED CompanyID 一致，法定全名规范化后与 TED 名称一致。GLEIF 的 `RA000065` 官方网站也指向该 Registry Agency，因此当前样本的 namespace 可以权威确认到 `RA000065`。

本研究只冻结以下最小字段：UIC、TED 名称、登记法定全名、法律形式原码、deed status 原码、官方查询 URL 和 `RA000065`。完整登记响应可能含个人或联系信息，只保存在临时 cache，不进入仓库。`legal_form_code` 和 `deed_status_code` 只按官方原值保存，不由本研究解释；例如 `РУДИН` 的 deed status 原码为 `1`，其余 6 条为 `2`，不能脱离 Registry Agency 枚举擅自改写成业务状态。

namespace 确认后，再以 `RA000065 + UIC` 查询 GLEIF。API 精确查询 7/7 均未观察到权威 LEI 记录；全量枚举同一 API 快照中 `entity.legalAddress.country=BG` 的 6,222 条记录、32 页后，7 个 UIC 的 `validatedAs` 命中和规范化法定名称/别名命中仍均为 0。该 API 快照时间为 `2026-10-25T16:00:00Z`，扫描摘要 SHA-256 为 `86411537768fc918ac9260bf07cb3b4279fb5314b7514eb46acafd0cb020eae5`。考虑到 GLEIF 官方说明 API 基于 Golden Copy，本研究随后下载并独立扫描了 GLEIF 官方 Concatenated LEI-CDF 3.1 文件：ZIP SHA-256 为 `23c03705b3f93dd9869af2c9366f1bc191640ac1fd0759e615ff768fc2d09af6`，XML `ContentDate` 为 `2026-10-25T09:00:01Z`，实际扫描 3,473,152 条且与 XML 头部总数一致；其中 6,222 条法律地址国家为 BG、5,698 条登记机关为 `RA000065`，7 个 UIC 的 `RegistrationAuthorityEntityID` 命中和法定名称/其他名称命中均为 0。摘要 SHA-256 为 `e87800e89cfbbb5d4bd85930cf4254bf3775436d14009fafa5f3c9e4fc6dc9dc`。因此，当前缺口不再是“本轮 API 是否漏召回”，而是“这些商业登记实体在该内容日期的 LEI 交付中没有匹配记录”；这仍不证明它们永久没有 LEI，也不能用名称候选补成全球身份。

跨来源映射结果：

| 分类 | 组织数 | 自动合并 |
| --- | ---: | --- |
| `authoritative_id_and_name` | 0 | 可以，但本样本没有 |
| `authoritative_namespace_no_gleif_match_observed` | 7 | namespace 已确认，但没有权威 LEI 命中 |
| `unique_exact_name_candidate_only` | 3 | 不可以，只能进入复核 |
| `no_exact_gleif_candidate_observed` | 19 | 不可以；也不能解释为“没有 LEI” |
| 合计需人工复核 | 29/29，100% | 不允许静默合并 |

三个唯一同名候选是 `THE BOEING COMPANY`、`HAMILTON SUNDSTRAND CORPORATION` 和 `VERTEX AEROSPACE LLC`。它们仍不是权威 crosswalk：USAspending UEI 的命名空间并不等于 GLEIF 记录的 `validatedAt + validatedAs`；TED 标识还混有国家登记号和平台 UUID，当前扁平响应没有提供足以映射到 GLEIF registration authority 的 namespace。即使名称唯一，也不能把候选 LEI 提升为 confirmed。

冻结与漂移门禁：

```text
TED XML 规范化提取：9616c1381435d1f2032336208756112c99a6885a581cb7445556fa2ae03aacba
TED 官方源 XML：f65386528d46a20f30ca6da69f2df8afcad09d077da0fc2634761932cd0f3f5a
保加利亚商业登记最小提取：48bfcd98d596b32392757480a67b9f09dd5a5499f63935886cf48658677927fd
保加利亚商业登记规范化记录：8f18545ecc20af9a53e0abfd93e85d5ead5ab1beaacb717598971c250d8d52ce
GLEIF 保加利亚登记机关集合：b2b7116589317ce03b96f9a2d7483971a4a73df9ffba0b43ffacac5f8d2a5110
29 个组织映射观测：dca565eb0444c2cd99f40d01fd9460a865b783cfc5286b43c012826c16667d95
```

XML 提取文件固定来源 URL、源 XML hash、XPath 语义、组织引用、名称、CompanyID、Country 和缺失的 scheme attributes；商业登记提取固定 7 个最小组织字段，并在运行时与 Registry Agency 当前响应逐条对比；如果本地存在官方 XML cache，评测还会重新解析 XML。映射哈希覆盖 29 个规范化组织输入、namespace 状态、映射分类和候选 GLEIF 权威字段。刷新公共 API 后，只要登记机关集合、商业登记名称/原码、GLEIF 候选、登记状态或分类变化，评测就会失败并要求审查差异，不能只更新数字。这里的两种 `no ... observed` 都是当前官方查询的观测结果，不证明组织永远没有 LEI；29/29 是本样本在当前严格映射策略下的复核量，也不能外推为全市场比例。

这一结果把“稳定 ID”拆成了三个不同问题：

1. 来源记录有没有本地 ID；
2. 名称与 ID 在原始结构中是否可证明地配对；
3. ID 是否声明了可验证的 namespace / registry authority；
4. 该 namespace 能否通过权威 crosswalk 映射到跨来源实体。

前两项已经可以由来源适配器解决；第三项在 7 个保加利亚组织上已由 Registry Agency 解决；第四项仍没有 LEI 命中，需要明确的 no-match 状态和人工裁决。它们都不自动要求通用 `DomainObject/Assertion` 平台。

## 6. 决策与下一个最小验证

当前机器判定为 **`dont_build_yet`**。这不是说结构化事实没有价值，而是说本轮已经找到一个与 E 持平的更小解法 C3，并且在冻结 challenge 上取消了其 operation/parameter oracle；采购标识研究又证明，当前更紧迫的缺口是来源结构、namespace 和 crosswalk，而不是通用 assertion 存储。下一步不再扩大仓库内人工题集，只验证三个仍未被独立证据覆盖的问题：

1. 使用未参与实现的评测者保管的真隐藏题集或真实 query log 时，确定性 planner 或 live planner 能否稳定规划到 C3 的正确工具和参数；
2. 冻结 29 个来源组织的人工裁决队列和裁决规范，并由至少两名非开发者记录每 100 个组织的处理量、分歧率和耗时；7 个保加利亚 no-match 已经由 API 与独立 Concatenated 文件双通道复核，但这只适用于所检查的内容日期；
3. 真实或授权脱敏工作流中，高 fan-out 聚合、历史时点和冲突裁决是否真的高频且会影响决策。

如果 C3 在真隐藏题集或真实 query log 上仍与 E 持平，停止本体 V1，只改进意图规划、实体解析和来源工具。只有当 E 在这三项上仍显示不可被 C3 替代的增益，才重新讨论 `Build small`。在此之前不进入数据库迁移、OpenAPI、前端关系图或通用本体编辑器。

## 7. 可复现方法

```bash
python scripts/validate_public_ontology_data.py \
  --cache-dir /tmp/knowledge-public-validation \
  --output /tmp/ontology-public-validation.json

scripts/test.sh --suite ontology-eval
```

第一条命令检查：

- 固定下载 URL 和 SHA-256；
- 文档、标签和 Evidence 数量；
- 每个 Evidence/answer offset 是否能回到原文；
- Award transaction 数量、修改号、金额守恒和更新时间；
- TED 修改通知对前一通知的引用、稳定买方 ID、标题和 CPV；
- LEI、历史名称和登记机关 crosswalk；
- 所有检查的机器可读总数、通过数和失败项。

第二条命令会从固定官方 ID 读取或复用缓存，在临时 PostgreSQL schema 中建立 Evidence corpus，真实调用 Knowledge 检索路径，并运行检索、planner、实体解析和标识覆盖门禁。它会写出：

- `.eval/ontology_public_pilot.json`：每题检索结果、trace、Evidence key、结构化答案、bootstrap 和 McNemar 结果；
- `.eval/ontology_public_pilot.md`：用于人工查阅的摘要。
- `.eval/ontology_planner_challenge.json`：每条 challenge 的规划、参数、拒答、答案和 Evidence 对比；
- `.eval/ontology_planner_challenge.md`：planner challenge 指标和门槛摘要。
- `.eval/ontology_entity_resolution.json`：GLEIF pair、全阈值扫描、详细混淆矩阵和决策；
- `.eval/ontology_entity_resolution.md`：实体解析对照摘要。
- `.eval/ontology_identifier_coverage.json`：来源内 ID 覆盖、TED 原始行配对、GLEIF 映射分类、候选详情和限制；
- `.eval/ontology_identifier_coverage.md`：采购稳定 ID 与人工复核下界摘要。

评测默认使用离线确定性 n-gram embedding/rerank provider，因此可复现但不代表真实模型质量。评测问题与事实表由同一批官方记录派生，不是独立隐藏测试集。C3 与 D/E 共用 oracle operation 和稳定 ID 参数，因此其 100% 只能否定“当前任务必须使用通用 assertion 层”，不能证明端到端产品已可用。

原始 ZIP 约 80 MB，只保存在指定 cache 目录，不提交仓库。公共 API 返回可能因官方更正而变化；固定对象 ID、归一化数据 SHA-256、映射观测 SHA-256 和断言式检查使变化会形成明确门禁，而不是静默覆盖既有结论。如果官方更正导致 hash 变化，必须审查原始差异、重跑指标并更新结论，不得只更改预期 hash。

TED 官方 XML 下载端点可能触发 CloudFront/WAF 浏览器挑战，因此评测不会用普通 HTTP 客户端伪装成已完成源 XML 刷新。需要重新验证时，使用浏览器从固定官方 URL 下载 `186732-2025.xml`，放入 `${KNOWLEDGE_TED_XML_CACHE_DIR:-/tmp/knowledge-public-ontology-pilot-cache/ted-xml}/186732-2025.xml`，再运行 `ontology-eval`。文件存在时，评测会先校验官方 XML SHA-256，再重新解析 Organization 引用；文件不存在时，只使用已冻结的规范化提取，并在 JSON 报告中把 `source_xml_revalidated` 标为 `false`。
