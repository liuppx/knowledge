# 运营本体 V1 实证研究方案

> 状态：研究协议；公开数据技术代理 pilot 已执行，真实工作流验证尚未执行。
>
> 日期：2026-10-25。
>
> 决策对象：Knowledge 是否应建设合同—产品—组织范围内的 `DomainObject / Assertion / Evidence / Release / Grant` 能力。
>
> 前置材料：[构建风险评审](运营本体V1构建风险评审.md)、[成功产品借鉴分析](运营本体成功产品借鉴分析.md)、[公开数据代理验证](运营本体V1公开数据代理验证.md)、[合成演练包](validation/ontology-v1/README.md)。

## 1. 研究目的

本研究不以证明“知识图谱有价值”为目标，也不预设 Knowledge 必须建设运营本体。它要回答一个可被否定的问题：

> 在真实合同—产品—组织工作流中，对象身份、带有效期和 Evidence 的断言、冲突并存、Release 历史视图与 Grant 权限，是否能够显著改善当前文本检索无法稳定完成的决策任务，并且收益是否足以覆盖数据治理和持续维护成本？

研究必须区分：

- **可实现性：** 技术上能否表达对象、关系和断言；
- **正确性：** 结构化结果是否符合原始来源、时间和权限；
- **增量价值：** 是否优于当前关键词和混合检索；
- **可运营性：** 非开发人员能否审核、维护和解释；
- **建设必要性：** 是否值得进入数据库、API 和前端实现。

## 2. 预注册决策

研究开始前冻结以下四种结论，完成后必须选择其中一种，不得使用含糊的“方向有潜力”：

1. **Don't build yet：** 当前检索已经足够，或没有真实工作流、权威来源和维护主体。
2. **Validate again：** 问题真实，但样本、身份、权限、标注一致性或统计证据不足。
3. **Build small：** 只建设被真实问题证明必要的对象身份、断言、Evidence、时态、冲突和 Release/Grant 能力。
4. **Evaluate graph backend：** 仅当产品价值已经成立，且 PostgreSQL workload 基准证明关系查询成为瓶颈时评估专用图系统。

任何结果都不能直接得出“建设通用企业本体”“接入员工 PII”或“引入图数据库”的结论。

## 3. 研究假设

### H1：决策正确性

对于必须使用对象身份、关系、时间或冲突状态的问题，人工维护的结构化事实视图加 Evidence，相比当前最佳文本检索基线，正确率至少提高 10 个百分点；配对差异的 95% bootstrap confidence interval 不跨越 0。

如果样本量不足以支持置信区间，报告 pilot 结果，不宣称统计显著。

### H2：证据完整性

所有被判定为正式正确的答案都必须能够定位到原始 SourceAsset 版本和具体 Evidence locator。正式答案 Evidence 可追溯率必须为 100%。

### H3：时态与 Release 正确性

对包含 `as_of` 或固定 Release 的问题：

- 当前有效性判断正确率目标不低于 95%；
- 固定 Release 重放结果必须 100% 一致；
- 新事实不能改变旧 Release 的答案。

### H4：对象身份

在高风险合同和组织对象上：

- entity resolution precision 目标不低于 98%；
- recall 目标不低于 90%；
- false merge rate 不高于 1%；
- 所有 uncertain pair 必须进入人工裁决，不自动合并。

如果样本太小，必须报告原始 TP、FP、FN、TN 数量，不能只报告百分比。

### H5：冲突和失效来源

- 已知冲突必须 100% 暴露；
- candidate 不得被表述为 confirmed；
- stale 或 missing Evidence 不得被无保留用作正式结论；
- superseded 事实不能进入当前有效视图，但必须保留历史可追溯性。

### H6：权限

对象、关系、属性、Evidence 和 Release 的未授权泄漏数必须为 0。不能用总体正确率或业务价值抵消权限泄漏。

### H7：可运营性

至少两名非开发人员在完成统一标注培训后，能够：

- 独立完成对象匹配和断言审核；
- 解释冲突和当前视图；
- 生成一致的 Release 候选结果；
- 不通过直接修改数据库完成维护。

如果只有开发者能维护事实模型，则 Build small 条件不成立。

## 4. 研究角色与职责分离

同一人不应同时编写所有问题、制作所有 gold answer、调试系统并完成最终评分。

| 角色 | 职责 | 不应承担 |
| --- | --- | --- |
| 数据负责人 | 授权和脱敏原始材料，确认来源系统 | 不直接调整系统答案 |
| 领域专家 A/B | 独立标注对象身份、断言和 gold answer | 不查看另一人的标注 |
| 裁决者 | 处理标注分歧并记录理由 | 不删除分歧记录 |
| 系统执行者 | 运行各实验组并保存原始输出 | 不查看隐藏测试集 gold answer |
| 安全评审者 | 设计和执行负向权限测试 | 不依赖正常流程自证安全 |
| 分析者 | 计算指标、置信区间和错误分类 | 不在看过结果后修改门槛 |
| 业务使用者 | 判断答案是否支持真实业务动作 | 不参与系统调参 |

若团队规模不足，可以一人承担多个角色，但必须记录角色冲突，并至少保持测试集 gold answer 对系统执行者隐藏。

## 5. 原始数据要求

### 5.1 最小真实样本

首轮正式研究建议至少包含：

- 20 份合同正文、附件、补充协议或修订版本；
- 10 个产品，包含至少 2 组旧编码或别名；
- 5 个组织，包含至少 2 组更名、简称或跨系统 ID；
- 5 组有效期变化或合同替代；
- 5 组来源冲突、范围重叠或草案/正式状态混淆；
- 3 组 SourceAsset 缺失、版本变化或 checksum 变化；
- 2 个不同 Release 的历史视图；
- 至少 2 类不同权限的服务主体。

这些数字是最低研究设计，不是产品容量目标。若真实数据不足，应缩小结论强度，而不是用大量合成数据补成“正式样本”。

### 5.2 一手材料

必须优先收集：

- 合同签署件、草案、模板、附件和补充协议；
- 合同状态和审批审计日志；
- 产品主数据原始导出；
- 组织或供应商主数据原始导出；
- 对象历史名称、外部 ID 和人工映射表；
- SourceAsset 版本、checksum、ETag 和 locator；
- 当前真实搜索 query、失败 query 和人工修正记录；
- 现有人工 Excel、脚本、工单和例外处理记录；
- Release、Grant、RetrievalLog 和 AgentRun 原始记录；
- 实际访问控制规则，而不是只有角色名称的概述。

不得仅使用现有调研文档、竞品摘要、整理后的 KnowledgeItem 或合成演练材料。

### 5.3 数据清单与授权

所有材料先登记到[原始数据清单模板](validation/ontology-v1/real-study/data_inventory.csv)，至少记录：

- 来源系统和业务负责人；
- 文件或记录的不可变标识；
- 版本和 checksum；
- 权威范围；
- 敏感级别；
- 是否允许进入研究环境；
- 是否允许引用给业务使用者；
- 删除和保留要求。

真实机密数据不得提交到公开仓库。模板可以进入仓库，数据本身应保存在获得授权的受控空间。

## 6. Competency Questions

正式问题集至少包含 40 个问题：

- 不少于 25 个关系、时态、冲突、Release 或权限决策问题；
- 不少于 10 个普通文本事实控制问题；
- 不少于 5 个无答案、证据不足或权限禁止的问题。

问题必须来自真实工作流或真实失败记录，不得为了已有 schema 人工编题。

每个问题记录在[问题集模板](validation/ontology-v1/real-study/competency_questions.csv)，并包含：

- 用户角色；
- 真实决策；
- 查询时间和 Release；
- 预期答案；
- 允许的“不确定”或“冲突”答案；
- 所需对象、关系和 Evidence；
- 错误后果；
- development/test split。

### 6.1 数据集划分

- 40% development set：用于完善标注规则、问题表达和实验管线；
- 60% hidden test set：冻结后不得用于调参；
- 同一合同系列、组织别名组或近重复问题不得跨 development/test 泄漏；
- 合成困难样本单独报告，不能混入真实测试集提高数量。

## 7. Gold Set 构建

### 7.1 对象身份金标

使用[实体解析金标模板](validation/ontology-v1/real-study/entity_resolution_gold.csv)记录 record pair：

```text
same
different
uncertain
```

标注者必须给出原始标识、名称、历史名称、地址或来源依据。不能只根据字符串相似度决定。

统计：

- raw agreement；
- Cohen's kappa；
- precision / recall / F1；
- false merge / false split；
- uncertain rate；
- 按合同、产品、组织分别报告。

对象身份关键字段一致性目标为 `kappa >= 0.80`。低于门槛时先修订标注指南，不进入系统比较。

### 7.2 断言金标

使用[断言金标模板](validation/ontology-v1/real-study/assertion_gold.csv)，从原文 span 标注：

- subject；
- predicate；
- object 或 literal；
- qualifier；
- `valid_from / valid_to`；
- polarity；
- modality；
- document status；
- Evidence locator；
- source authority；
- candidate/confirmed/disputed 等状态。

两名领域专家独立标注，再使用[裁决日志](validation/ontology-v1/real-study/adjudication_log.csv)保存最终决定和原因。

断言关键字段 Krippendorff's alpha 或等价一致性目标为 `>= 0.75`。时间范围、否定和 Evidence locator 应单独报告一致性，不能只计算总平均。

### 7.3 Gold Answer

每个 competency question 的 gold answer 必须包括：

```text
answer
answer_status
as_of
release
supporting_assertions
supporting_evidence
conflicting_assertions
permission_expectation
adjudication_note
```

Gold answer 可以是“未知”“冲突”“Evidence 缺失”或“无权访问”。不能强迫所有问题得到单一肯定答案。

## 8. 实验组

同一测试问题在同一 SourceAsset 版本和权限上下文下运行以下组别：

| 组别 | 方法 | 目的 |
| --- | --- | --- |
| A | 当前关键词检索 | 最低基线 |
| B | 当前混合检索 | 当前最佳检索基线 |
| C | 混合检索 + 现有 metadata filter | 判断简单过滤是否已经足够 |
| D | 人工事实表结构化查询 | 无代码验证对象/断言模型本身的价值 |
| E | 人工事实表 + Evidence 检索 | 验证结构化过滤与原文解释组合 |
| F | E + 当前 rerank/回答生成 | 验证最终消费体验，不作为事实正确性的唯一来源 |

在正式代码实现之前，D/E 可以使用经审核的 CSV 或 JSON 事实表人工执行。若 D/E 不显著优于 B/C，不进入数据库实现。

## 9. 消融实验

只有完整组优于基线还不够，需要分别移除：

1. 对象身份映射；
2. valid time；
3. Release 固定；
4. 冲突状态；
5. Evidence 健康状态；
6. 权威来源排序；
7. Grant 过滤。

观察每项移除后哪些问题失败。一个没有造成任何可观察差异的字段或机制，不应自动进入 V1。

## 10. 评价指标

### 10.1 答案质量

- decision accuracy；
- 结构化字段 exact match；
- temporal correctness；
- conflict disclosure rate；
- unknown/abstention correctness；
- unsupported claim rate；
- stale-fact usage rate。

### 10.2 检索与引用

- Recall@k；
- MRR；
- nDCG；
- citation precision；
- citation recall；
- Evidence locator correctness。

### 10.3 对象身份

- precision / recall / F1；
- false merge rate；
- false split rate；
- 来源内 ID 覆盖率；
- 名称—ID 可验证配对率；
- identifier namespace / registry authority 可解析率；
- 权威 crosswalk 覆盖率；
- uncertain rate；
- 每 100 个组织的人工裁决量和裁决耗时。

### 10.4 产品与运营

- 完成一次决策所需时间；
- 切换系统次数；
- 人工修正次数；
- 每条候选断言的审核时间；
- 每次 Release 的冲突数和处理时间；
- SourceAsset 变化到 stale 被发现的时间；
- 非开发人员完成维护的成功率。

### 10.5 安全

- 未授权对象泄漏数；
- 未授权关系泄漏数；
- 未授权 Evidence 泄漏数；
- 通过返回数量、错误信息或关系路径产生的侧信道泄漏；
- Grant 撤销后的残留访问；
- 固定旧 Release 是否绕过当前权限。

## 11. 评分和统计计划

### 11.1 单题评分

每个决策问题按以下维度分别评分，不只给一个总分：

| 维度 | 0 | 1 |
| --- | --- | --- |
| 结论 | 错误或无依据 | 与 gold answer 一致 |
| Evidence | 无法定位或错误 | 定位正确来源和位置 |
| 时间 | 忽略或判断错误 | as_of 语义正确 |
| 冲突 | 静默覆盖 | 正确展示冲突和状态 |
| 权限 | 泄漏或错误拒绝 | 与权限预期一致 |
| 不确定性 | 编造确定答案 | 正确 abstain 或标记 unknown |

高风险问题只有所有必要维度均为 1 才算通过。

### 11.2 配对分析

- 同一问题比较 B 与 E/F，优先使用 McNemar test 分析配对正确/错误；
- 使用 bootstrap 计算正确率、引用率和耗时差异的 95% confidence interval；
- 同时报告 effect size 和原始问题数；
- 普通文本题与关系/时态题分开报告；
- 厂商或模型成本不能与准确率混成单一加权分数。

### 11.3 失败分类

所有失败至少归入：

```text
source_missing
parse_error
entity_resolution_error
predicate_error
temporal_error
conflict_suppressed
authority_error
release_error
permission_error
retrieval_error
generation_error
gold_ambiguity
```

不能使用“模型效果不好”作为最终错误类型。

## 12. 安全验证

建立：

```text
principal × object type × relation type × property × evidence × release
```

权限矩阵，并执行：

- 正向访问；
- 无 Grant；
- expired/revoked Grant；
- 对象可见但敏感属性不可见；
- 对象可见但 Evidence 不可见；
- 关系一端可见、另一端不可见；
- 固定旧 Release；
- 邻接数量和错误信息侧信道；
- Agent 连续查询拼接敏感事实。

任何真实敏感数据泄漏立即终止研究，不等待最终统计。

## 13. 变形测试与不变量

研究结果必须能够转化为可执行不变量：

1. `as_of > valid_to` 时，断言不能进入当前有效视图；
2. 新事实不能改变已发布旧 Release；
3. Evidence 变为 missing 后，相关正式断言进入 stale 或待复核；
4. candidate 不能覆盖 confirmed；
5. disputed 必须保留分歧和双方 Evidence；
6. revoked Grant 不能通过旧缓存或旧 Release 继续访问；
7. 对象改名不能改变稳定对象 ID；
8. merge 必须可审计，错误 merge 必须可恢复；
9. 同一输入版本和同一 Release 的结构化结果必须确定；
10. 无权访问的关系不能通过计数或路径推断。

这些不变量后续可以转换为数据库约束、领域服务测试和 property-based tests，但本研究阶段先人工验证语义是否正确。

## 14. 可复现性

每轮实验使用[实验结果模板](validation/ontology-v1/real-study/experiment_results.csv)和不可变 manifest，记录：

- 数据集 ID 和 checksum；
- 问题集版本；
- gold answer 版本；
- source、object、assertion schema 版本；
- 代码 commit；
- 配置；
- 检索模式；
- 模型、embedding、reranker 和 prompt 版本；
- 随机种子；
- principal、Release 和 as_of；
- 原始答案和引用；
- 时延和成本；
- 人工评分与裁决。

最终研究必须满足：另一名未参与实现的人员可以根据 manifest 和一条明确命令重新生成实验输出和报告。

## 15. 进入 Build Small 的硬门槛

只有全部满足，才进入窄范围 V1 需求和技术设计：

1. 真实关系/时态问题不少于 25 个；
2. 对象身份和断言标注一致性达到预设门槛；参与自动合并的对象还必须能够说明 identifier namespace、registry authority 和权威 crosswalk，唯一同名候选不算通过；
3. 结构化事实加 Evidence 在关系/时态题上相对当前最佳基线至少提高 10 个百分点，或形成等价强度的明确业务收益；
4. 正式答案 Evidence 可追溯率为 100%；
5. 时态正确率不低于 95%；
6. 已知冲突 100% 暴露；
7. stale/candidate 不被误用为正式事实；
8. 权限泄漏为 0；
9. 固定 Release 100% 可重放；
10. 至少两名非开发人员可以完成审核和解释；
11. 至少一个真实工作流的耗时、错误或升级次数有可测改善；
12. 维护成本没有超过业务团队愿意承担的明确上限。

第 12 项的具体上限应由业务负责人在 development pilot 后、hidden test 前冻结，不能由系统团队单方面决定。

## 16. 停止条件

出现以下任一情况，应停止实现扩张并返回问题定义：

- 无法取得真实或授权脱敏的原始材料；
- 没有稳定对象 ID，也没有负责裁决身份的人；
- 标注专家对核心事实长期无法达成一致；
- 当前混合检索已达到相同决策质量；
- 结构化事实只改善展示，没有改善判断；
- 业务团队不愿承担事实维护和冲突裁决；
- 权限边界无法在对象、关系和 Evidence 层说明清楚；
- 所有收益都来自人工提前整理答案，而不是模型机制本身；
- 只有引入员工 PII 或扩大到更多业务域才能显示价值。

## 17. 研究交付物

正式研究完成时必须提供：

1. 原始数据清单和授权说明；
2. 真实工作流和关键失败事件；
3. 冻结的 competency questions；
4. 对象身份 gold set；
5. 断言和 Evidence gold set；

## 18. 当前状态

当前仓库没有内部真实或授权脱敏的合同、产品和组织样本，无法执行能够证明真实产品需求的正式研究。与此同时，[公开数据代理验证](运营本体V1公开数据代理验证.md)已经：

- 完成 ContractNLI、CUAD、USAspending、TED 和 GLEIF 的 25/25 项来源完整性与关联检查；
- 用 25 个固定官方对象族（10 个 Award family、10 条 TED 通知链、5 个 LEI）、129 条 Evidence 和 50 个问题运行 Knowledge 技术代理 pilot；
- 确认 `top_k=6` 时 E 相对 C2 的基线差异通过预先冻结的效应门槛；
- 通过事后 top-k 稳健性检查发现，当同族检索窗口达到 15 条时 C2 已与 E 持平，基线差异不稳健。
- 确认不建立通用 assertion 投影的来源原生工具 C3，在共用 oracle 意图和稳定 ID 时，对 50 个问题的正确性、Evidence 可追溯性和拒答与 E 持平。
