# 模块化复用与前端工程化规划

状态：规划基线

## 1. 总体方向

Knowledge 当前的 FastAPI 控制台是过渡实现。后续前端工程进入仓库根目录的 `web/`，通过独立的工程化构建、路由、状态管理和组件系统承载正式产品界面。

Knowledge 后端继续保留领域控制面，但不再把文档解析、连接器、索引和 Agent 执行实现为不可替换的内部代码。成熟开源项目优先采用源码搬入后的本地适配方式复用：先把必要模块纳入 `knowledge/third_party`，再围绕 Knowledge ports 做瘦适配和裁剪。只有当模块边界过重或许可证不允许时，才参考其设计自行实现。

## 2. Knowledge 自有领域

以下数据和规则由 Knowledge 拥有，不能由外部 RAG 或应用平台替代：

- Source、SourceAsset、EvidenceUnit
- KnowledgeItem、Revision、Candidate
- KBRelease、ReleaseItem
- ServicePrincipal、ServiceGrant
- RetrievalLog
- AgentRun、Artifact、Context Reference 和 provenance
- Warehouse 资产引用、checksum、版本冻结和发布范围

这些对象构成稳定的领域 API。外部项目产生的文档、chunk、检索结果或运行结果，必须转换为 Knowledge 的引用和证据，不直接暴露其内部数据库模型。

## 3. 可替换能力边界

后端应逐步形成以下 ports，具体实现放在 adapters 中：

```text
SourceConnector   外部来源发现、增量同步、删除通知和 ACL
DocumentParser    文档解析、结构识别、文本和位置元数据
IndexBackend      chunk、embedding、索引写入和删除
Retriever         检索、过滤、引用和 rerank
ArtifactStore     分析产物和 manifest 的读写
RunExecutor       Agent Run 的任务执行和进度回报
```

源码搬入与适配器示例：

```text
third_party/onyx
third_party/ragflow
adapters/warehouse
adapters/onyx
adapters/ragflow
adapters/local_db
adapters/duckdb
```

第三方源码先集中放在 `third_party`。适配器只能通过 ports 与领域服务通信，不能把第三方项目的实体模型、数据库连接或前端组件泄漏到 Knowledge 领域层。

## 4. 外部项目复用策略

### Onyx

优先搬入并评估连接器、ACL 同步、混合检索和检索接口相关代码。Onyx 的 Agent、Artifacts 和用户界面继续归 Chat/Agent 或 `web/`，不并入 Knowledge 领域。

复用顺序：搬入明确 MIT 范围内的独立代码 > 编写 Knowledge adapter > 裁剪依赖和领域模型。Onyx `ee` 目录使用单独的企业许可证，不能按整个仓库 MIT 处理，也不能复制进当前项目。

### RAGFlow

优先搬入并评估复杂文档解析、chunk 引用、混合检索和 rerank。RAGFlow 的结果必须保留 Warehouse checksum、文档版本和位置映射，转换为 Knowledge 的 `SourceAsset`/`EvidenceUnit`。

RAGFlow 使用 Apache-2.0。源码搬入后仍要避免把其内部存储、任务系统和升级约束带入 Knowledge 领域模型。

### Dify / FastGPT

仅在需要工作流、Agent 应用编排或低代码产品能力时评估。它们不作为 Knowledge 的知识治理基座，避免重复拥有知识库、授权、发布和 Run 状态。

### 自研替代

如果第三方许可证不适合目标部署方式，或其实现无法满足 Warehouse 版本冻结、Evidence 定位和审计要求，则停止搬入对应模块，参考公开接口和架构自行实现。自研代码不得复制受限制的实现细节、商标和前端资产。

## 5. `web/` 前端工程

`web/` 是正式前端工程，负责：

- 路由、登录态、知识库工作区和发布管理界面
- Source、Evidence、Knowledge Item、Release 和检索审计视图
- AgentRun 进度、产物和错误状态
- API client、类型生成、表单校验、缓存和组件系统

FastAPI 当前的 `knowledge/templates` 和 `knowledge/static` 保留为迁移期间的 fallback，不再扩展复杂交互。新功能优先进入 `web/`，API 通过 OpenAPI 契约调用后端。

## 6. 分阶段实施

1. 冻结领域 API 和 ports，不改变 Evidence、Item、Release、Grant、RetrievalLog、AgentRun 的语义。
2. 建立 `web/` 最小工程，先迁移登录、知识库选择、资产和检索验证页面。
3. 把 RAGFlow parser/chunker 与 Onyx connector 相关源码搬入 `knowledge/third_party`，保留来源、commit 和许可证记录。
4. 把现有 parser、embedding、vector store 包装为默认 adapter，保持现有测试通过。
5. 在 vendored 源码之上分别实现 Onyx connector/retriever 和 RAGFlow parser/retriever 的小规模 PoC。
6. 用真实 Warehouse 文件验证版本冻结、引用定位、删除同步、发布固定和审计闭环。
7. 只有适配器通过验收后，才替换默认实现；失败时可以退回本地 adapter。

## 7. 验收标准

- 更换索引或解析后端不修改 Knowledge 领域模型。
- 任意检索结果都能追溯到 Warehouse asset、版本或 checksum 和位置。
- 外部连接器的 ACL 不会绕过 ServiceGrant。
- 发布版本可以固定检索范围，不受外部索引实时变化影响。
- AgentRun、Artifact 和检索审计不依赖第三方数据库。
- 前端只依赖公开 API，不直接读取 Knowledge 数据库或第三方服务数据库。
