# Knowledge 产品验证知识库

## 1. 验证目标

使用 `knowledge` 项目自身的正式文档验证完整产品链路：

1. 多篇 Markdown 接入与索引。
2. 文档、chunk、evidence 与正式知识项的可追溯性。
3. 用户无需了解内部接口即可浏览知识并验证检索。
4. 检索结果能够区分直接事实、跨文档流程和无依据问题。
5. 切换知识库后不会混入其他工作区的数据。

建议知识库名称：`Knowledge Product Handbook`。

## 2. 语料范围

第一轮导入以下 11 篇当前有效文档：

- `docs/README.md`

- `docs/社区产品关系与开发边界.md`

这两篇描述未来目标和待办事项，不应与当前正式事实混合发布。

## 4. 评分标准

每个问题按 0 到 3 分评分：

- `3`：结论准确，覆盖关键约束，并能定位到正确来源。
- `2`：主体结论准确，但遗漏一个重要限制或来源不完整。
- `1`：包含部分相关信息，但结论含混、拼接错误或引用弱相关内容。
- `0`：没有命中、答非所问或编造语料中不存在的能力。

总分为 36 分：

- `32-36`：可进入下一阶段真实业务语料验证。
- `26-31`：基本可用，需要优化切片、知识整理或排序。
- `18-25`：检索链路可运行，但知识质量不足。
- `<18`：不应继续扩充语料，应先修复导入与检索基础问题。

Q12 是否定性测试。若系统编造发布能力，该题直接记 0 分，并将问题标记为高优先级。

## 5. 产品体验检查

除答案质量外，每轮验证记录以下体验指标：

- 从创建知识库到首个文档可见所需的操作次数。
- 用户是否能判断文件正在上传、排队、处理或失败。
- 导入完成后，是否能自然进入来源文档或知识地图。
- 知识项详情是否能看懂来源、Evidence、revision 和发布状态。
- 检索无结果时，界面是否给出可执行的下一步。
- 切换知识库后，旧知识库内容是否完全消失。
- 刷新浏览器后，是否恢复到上次使用的知识库。

## 6. 第一轮通过条件

第一轮验证通过需要同时满足：

1. 11 篇文档全部导入成功，没有静默跳过。
2. 文档列表能显示文件级处理状态和 chunk 数量。
3. Q01-Q11 至少 9 题获得 2 分以上。
4. Q12 不产生无依据结论。
5. 每个正式知识项可以回查至少一个 Evidence。
6. 知识库切换和刷新恢复不发生数据串库。

## 7. 自动化验收脚本与运行记录

`scripts/product_acceptance.py` 用本文 §2 的 11 篇文档，经真实 HTTP 接口走完整链路（Warehouse 凭证 → 上传 → 绑定导入 → 文档可见 → 扫描/Evidence → 候选/接受 → 发布 → Q01–Q12 search-lab → Service Principal + Grant 经 `/service/search` 检索 → 第二知识库隔离），输出 Markdown 报告到 `.eval/acceptance_report.md`。默认 in-process 跑在 `knowledge_test` 库 + mock Warehouse/模型；`--base-url` 可指向真实部署。§6 中可自动判定的条件（1、2、5、6）与检索层的「预期来源是否进入 top-6」由脚本给出；条件 3/4 的答案评分仍需人工。
