# 混合检索与真实模型落地设计（v1.0）

> 关联：[知识库能力规划与快速上线路线](知识库能力规划与快速上线路线.md) 中 v1.0 的两项「必做」——混合检索（BM25/关键词 + 向量 + rerank）与经 Router 的真实模型/embedding。本设计给出可落地的实现路径、契约影响、迁移方案与评测门禁。

## 1. 现状（为什么这一步是「接缝」而非「新建」）

代码探查结论：**检索读路径与向量子系统当前完全断开**。

- **检索读路径（关键词 only）**：`/service/search`、`/service/search/formal`、`/service/search/evidence` → `ServiceSearchService.search()`（`knowledge/services/service_search.py:69`）→ `_search_formal` / `_search_evidence`。打分是纯 token-overlap：`_text_score()`（`service_search.py:409`）= 查询词交集比例 + 0.2 短语命中加分。**不触碰任何 embedding 或向量库。**
- **向量子系统（写路径已通，读路径悬空）**：ingest 时 `IngestionService` 用 `build_embedding_provider()` 生成向量、存入 `EmbeddingRecord.vector_json`（JSON 列，非 pgvector），或推入 Weaviate。`build_vector_store().search()`（`knowledge/services/vector_store.py`，`DBVectorStore.search:63` / `WeaviateVectorStore.search:270`）**有实现、有测试（`tests/test_provider_consistency.py`），但无任何生产调用方**。
- **真实模型接入点已存在**：`build_embedding_provider()`（`knowledge/services/embedding.py:89`）在 `model_provider_mode=="openai_compatible"` 且配置了 `model_gateway_base_url` 时返回 `OpenAICompatibleEmbeddingProvider`，否则 `MockEmbeddingProvider`。外部模型 HTTP 调用范式见 `SpreadsheetPlanningProvider`（OpenAI 兼容 `/v1/chat/completions` + Bearer key）。

**因此 v1.0 的工作 = 把悬空的向量读路径接进 `ServiceSearchService`，加入融合与 rerank，并让 embedding/rerank 走真实 Router；不是从零建检索。**

## 2. 目标与非目标

**目标（v1.0）**
1. `/service/search*` 三个端点内部升级为混合检索；**对外响应结构与三模式语义（formal_first / formal_only / evidence_only）保持不变**。
2. embedding 与 rerank 经 Router 接真实服务，固定模型版本、超时、重试、降级与成本可控。
3. 权限/可用性过滤严格前置（沿用现有 release/grant/availability 解析）。
4. 一套可复跑的检索评测（Q01–Q12）作为质量门禁。

**非目标**
- 不引入对话/模型渠道管理/智能体界面（越界，属 Chat/Router/Agent）。
- 不采用 pgvector 路线（v1.0 定为 Weaviate，见 §7）。
- 不改变 `/service/*` 冻结契约的路径与方法。

**已定决策**（产品拍板）
- 向量存储：**v1.0 直接切 Weaviate**（`vector_store_mode="weaviate"`），DB 模式仅作为无 Weaviate 时的本地/测试回退。
- rerank：**v1.0 默认开启**（`retrieval_rerank_enabled=True`），依赖 Router rerank 服务就绪；失败降级到 RRF（§6）。

## 3. 检索管线（目标架构）

```
query
 └─ 权限/可用性过滤前置（release + grant + availability_mode）        [已存在]
     └─ 双路召回（并行）
         ├─ 关键词召回  _text_score（保留，作为一路信号）
         └─ 向量召回    embed_query(query) → vector_store.search(top_k=N)
     └─ 融合  Reciprocal Rank Fusion (RRF)                          [新增]
     └─ rerank（可选，flag 控制）  Router rerank(query, candidates)   [新增]
     └─ 截断 top_k + 三模式组装 + RetrievalLog                       [已存在，扩展 trace]
```

**关键设计决策**

- **融合用 RRF 而非加权分数**：关键词分（0–1.2）与余弦相似度（-1–1）量纲不可比，归一化脆弱。RRF `score = Σ 1/(k + rank_i)`（k=60 惯例）只依赖排名，稳健、无需调参、易解释。融合在 formal 与 evidence 各自内部进行，保持两类结果的语义边界。
- **重要架构发现——检索粒度错位**：`/service/search*` 产出的是 **evidence unit / knowledge item revision**（治理过的单元），而 chunk 级 `EmbeddingRecord`（`chunk_id` 键）来自原始文档；`EvidenceUnit` 无 `chunk_id`，两者无直接连接（仅有 `EvidenceUnit.vector_status` 预留位）。因此**不能**简单地把 `vector_store.search()` 的 chunk 命中映射回 evidence 单元（source_path 级映射太粗，会错误地整篇加权）。
- **分两步接向量信号**：
  - **PR-1（本步，已完成）——lexical 召回集上的混合重排**：对已通过权限过滤 + 关键词召回的候选，按 `embed_query(query)` 与候选文本（evidence.text / title+statement）的余弦得到语义排名，与关键词排名 RRF 融合重排。**仅在真实 embedding provider 下激活**；mock（测试/开发默认）走关键词-only，保证确定性。任一 embedding 失败降级为关键词-only（trace 标记）。这是诚实的「混合重排」，召回集仍由 lexical 决定。
  - **PR-2——真正的向量召回扩展**：为 evidence 落**单元级** embedding，查询时以向量召回补齐 lexical 漏召的语义命中，再与关键词候选并集后 RRF。融合逻辑与 PR-1 一致，仅扩宽召回来源。**PR-2a（已完成）**先以 Postgres `unit_embeddings` 表做后端（逐 KB 余弦），端到端可测；**PR-2b** 再切 Weaviate ANN 后端与真实 embedding。
- **rerank 为默认阶段、可降级**：`retrieval_rerank_enabled` **默认 True**。对 RRF 前 M 名调用 Router rerank，用 rerank 分重排；rerank 失败/超时降级为 RRF 结果（见 §6）。flag 保留用于灰度与排障。
- **三模式语义保持**：formal_only/evidence_only 各自跑混合；formal_first 先 formal，不足 top_k 再补 evidence（沿用现有 `service_search.py` 逻辑与去重）。

## 4. 真实模型 / Router 接入

| 能力 | 现有适配 | v1.0 动作 |
|---|---|---|
| Embedding | `OpenAICompatibleEmbeddingProvider`（`embedding.py:54`） | 复用。Router 若 OpenAI 兼容，仅需把 `MODEL_GATEWAY_BASE_URL`/key/`EMBEDDING_MODEL` 指向 Router |
| Rerank | 无 | **新增** `RerankProvider`（Mock + OpenAI/Cohere 兼容 rerank HTTP），工厂 `build_rerank_provider()` 按 `model_provider_mode` 选择 |
| 生成模型 | `SpreadsheetPlanningProvider` | 检索本身不需要生成模型；不在本步扩展 |

- 保持既有约定：`model_provider_mode ∈ {mock, openai_compatible}`，非 development 环境 `mock` 已被启动守卫拒绝（`settings.py:157`）。rerank provider 同样在 openai_compatible 下走真实、否则 mock。
- **成本/稳定性策略**（写进 settings，见 §8）：每类调用固定 model、timeout、max_retries（指数退避）、batch 大小；embedding 查询侧单条、ingest 侧批量。

## 5. 维度与再嵌入迁移（必须处理，否则切真实模型即坏）

- 现状 `embedding_dimensions=32`（`settings.py:84`，mock 用），真实 `text-embedding-3-small`=1536。**切 provider 后向量维度变化，Weaviate class 的向量维度在写入时固定，混入不同维度会导致查询失败或垃圾分。**
- 方案（Weaviate 语境）：
  1. Weaviate class（`weaviate_index_name`，默认 `KnowledgeChunk`）的维度由首批写入决定。**切换 embedding 模型/维度 = 重建 class + 全量重索引**，不可就地混维。
  2. `EmbeddingRecord.embedding_model` 仍作为真源账本：查询与回填以当前 `embedding_model` 为准；DB 回退模式下按 model 过滤召回。
  3. 提供**再索引回填**命令（幂等）：按 kb 重新 `embed_texts` 并 `vector_store.index_chunks(...)` 推入 Weaviate（`vector_store.py:index_chunks`），完成前该 kb 自动降级为关键词-only（按已索引数判定）。
  4. 切换真实模型的运维顺序：设置 Router → （若换维）重建 Weaviate class → 全量再索引 → 验证已索引数 → 才对外提供向量召回。
- `embedding_dimensions` 默认改为与所选真实模型一致（如 1536），mock 测试用小维保持快。

## 6. 失败与降级（检索不能因模型抖动而挂）

- **embedding 查询失败/超时**：降级为关键词-only，`RetrievalLog.trace` 标记 `vector_degraded=reason`，返回 200（不 500）。
- **Weaviate 不可达/超时**：同样降级为关键词-only，trace 标记 `vector_backend_degraded`；不因向量后端抖动而 500。
- **rerank 失败/超时**：降级为 RRF 结果，trace 标记 `rerank_degraded`。
- **某 kb 未完成再索引**：自动关键词-only（见 §5）。
- 所有降级路径进 `RetrievalLog`，便于评测与运维复盘。

## 7. 存储与扩展性（v1.0 = Weaviate）

- v1.0 采用 `WeaviateVectorStore`（`vector_store_mode="weaviate"`，`vector_store.py:128`），ANN 索引，避免 DB 模式 O(n) Python 余弦的扩展性天花板。
- **新增部署依赖**：Weaviate 服务需进 docker-compose（本地/生产）、CI（见 §10）与运维基线。连接参数已有：`weaviate_url/host/scheme/port/grpc_port/api_key`（`settings.py:70-76`）。
- `DBVectorStore` 保留为**无 Weaviate 时的回退**（本地快速起步、单测），由 `build_vector_store()`（`vector_store.py:338`）按 `vector_store_mode` 选择——设计不锁死后端（`IndexBackendPort` 抽象）。
- 运维基线需覆盖：Weaviate 健康检查（`WeaviateVectorStore.health`）、class 生命周期（重建=换维时）、备份/重建后的再索引流程。

## 8. 新增配置项（`knowledge/core/settings.py`）

```
retrieval_hybrid_enabled: bool = True      # 关闭则回退纯关键词（灰度/排障开关）
retrieval_vector_top_k: int = 20           # 向量召回候选数（融合前）
retrieval_rrf_k: int = 60                  # RRF 常数
retrieval_rerank_enabled: bool = True      # v1.0 默认开启；失败降级 RRF，flag 供灰度/排障
rerank_model: str = "rerank-english-v3.0"  # rerank 模型版本
rerank_top_m: int = 20                     # 送入 rerank 的候选上限
rerank_timeout_seconds: int = 10
rerank_max_retries: int = 1                # 仅重试传输错误 / 5xx，4xx 直接失败
embedding_timeout_seconds: int = 30        # 查询与批量回填共用（OpenAIEmbeddings request_timeout）
embedding_max_retries: int = 2             # 客户端内指数退避
```

（`retrieval_top_k=6` 保持为最终返回数。生产守卫可选扩展：openai_compatible 下 rerank_enabled 但缺 rerank 配置时告警。）

## 9. 契约影响

- **路径/方法零变更**——`/service/search*` 仍是冻结的三端点，`tests/test_openapi_contract.py` 门禁不受影响。
- 响应体保持现有 result views（`schemas/service_search.py`）。**可选**在 result item 增加非破坏性 `retrieval` 元信息（命中来源：keyword/vector/rerank、分数），默认可关，避免消费方（Chat/Agent/Project）被动升级。若增加字段，重新导出 OpenAPI 并过防漂移门禁。

## 10. 评测门禁（Q01–Q12）

- `tests/eval/` 固定问答集：问题逐字取自《产品验证知识库》§3 的 Q01–Q12，`expected` 为「预期主要来源」文档键；语料为 §2 所列 11 篇文档的摘写片段（27 段，关键事实与原文一致），CI 规模、确定性可复跑。Q12 无金标文档，检索层只记录命中（信息项），「无依据」判定属于答案层。
- 评测脚本（`tests/eval/harness.py`）对同一语料跑三档：关键词-only / 混合 / 混合+rerank（仅切换产品 flag，被测代码是真实 `ServiceSearchService` evidence 路径），产出 hit@k、Recall@k、MRR 与逐题首命中名次，写入 `.eval/retrieval_report.{json,md}`。
- 门禁断言（`tests/eval/test_retrieval_eval.py`，marker `eval`，默认 pytest 运行排除）：三档均真正启用（trace 校验，防止 mock 静默跳过抬高对比）；混合+rerank 的 hit 率与 MRR 不劣于关键词-only；混合+rerank 在 Q01–Q11 至少命中 9 题（对应《产品验证知识库》§6 条件 3，`KNOWLEDGE_EVAL_MIN_HITS` 可调）。
- Provider：默认 `KNOWLEDGE_EVAL_PROVIDER=offline`，使用离线确定性替身（ASCII 词 + CJK 二元组特征哈希 embedding / 同特征余弦 rerank），**只用于让三档真实分化并验证链路，不是质量参考**；`KNOWLEDGE_EVAL_PROVIDER=live` 用同一 harness 跑真实 Router provider（需 `MODEL_PROVIDER_MODE=openai_compatible`），v1.0 验收以 live 一轮为准并归档报告。
- 接入统一入口：`scripts/test.sh --suite eval`；CI job `eval-report` 为**非阻塞**（`continue-on-error`），报告写入 job summary 并上传 artifact，基线稳定后转阻塞。
- **首轮基线发现（已修复）**：`ServiceSearchService._tokenize` 原先只提取 `[A-Za-z0-9_]+`，中文查询在关键词路径上**零 token**，离线基线关键词档仅 4/11 命中；改为 ASCII 词 + CJK 字符二元组后关键词档 11/11、MRR 1.0（`tests/test_service_search_tokenize.py`）。在 27 段摘写语料上三档随后持平，说明该规模语料不足以区分混合与关键词的增益——增益判断留待 live 一轮与真实全文导入。
- **CI/测试对 Weaviate 的依赖**：单测与 eval 默认走 DB 回退（`vector_store_mode="db"`）保持快、无外部依赖；Weaviate 仅是 ANN 加速层，不改变排序语义，其真实往返由 `weaviate-roundtrip` job 覆盖。

## 11. 分阶段落地（PR 拆分，每步独立可测可回滚）

1. **PR-1 lexical 召回集混合重排 + RRF（已完成）**：`ServiceSearchService` 在关键词候选上加语义余弦排名并 RRF 融合（`_rank_entries`），`retrieval_hybrid_enabled` flag + 真实 provider 门控 + 降级路径，trace 记 `hybrid` 元信息。单测 `tests/test_service_search_hybrid.py` 用注入的确定性 provider 验证重排 / mock 跳过 / 降级 / disabled 四条路径；既有 164 用例（mock 路径）不变。
2. **PR-2a 单元级向量召回（DB 后端，已完成）**：新增 `unit_embeddings` 表（`UnitEmbeddingRecord`，`unit_kind`/`unit_id` 多态键，迁移 `d72569034d1a`）与 `knowledge/services/unit_retrieval.py`（`UnitEmbeddingIndexer` 幂等回填 + `DBUnitVectorIndex` 逐 KB 余弦打分）。`_search_evidence` 改为在权限过滤后的候选池上，用已回填的单元向量把 lexical 漏召的语义命中并入候选（`retrieval_vector_top_k`），再交给 PR-1 的 RRF 融合；无回填 / mock / embedding 失败均降级为 lexical-only（trace 记 `vector_signal`/`vector_widened`）。新增 owner-scoped `POST /kbs/{kb_id}/reindex-units`（幂等回填触发，非 `/service/*` 冻结面）。端到端单测 `tests/test_service_search_recall.py` + `tests/test_reindex_units.py` 用注入 provider 全程可测、零外部依赖。
3. **PR-2b Weaviate 上线 + 真实 embedding 切换 + 再索引运维（代码 + CI 已落地）**：`build_unit_vector_index()` 按 `vector_store_mode` 路由到 `WeaviateUnitVectorIndex`（独立 class `weaviate_unit_index_name`，Postgres 为真相源、Weaviate 为可重建 ANN 加速层），reindex 时镜像写入（best-effort，响应报 `weaviate` 状态），读路径对后端异常降级 lexical-only。`compose.yaml`/CI 增 Weaviate 服务；CI `weaviate-roundtrip` job 跑 `tests/test_weaviate_unit_index.py` 验证真实 upsert/near_vector 往返，本地无 Weaviate 自动 skip。运维顺序（上线/再索引/切维/降级）见《向量索引运维手册》。真实 embedding 网关切换仍需 `MODEL_PROVIDER_MODE=openai_compatible` + 网关就绪后按手册 §4 全量再索引。
4. **PR-3 rerank provider（默认开启，已完成）**：新增 `knowledge/services/rerank.py`（`RerankProvider` 基类 + `MockRerankProvider` 确定性离线打分 + `OpenAICompatibleRerankProvider` 走 Router `POST /rerank` + `build_rerank_provider()` 按 `model_provider_mode` 选择）。`ServiceSearchService` 在 RRF 融合后、`top_k` 截断前对前 `rerank_top_m` 名调 rerank 重排（`_rerank_entries`，经 `_emit` 统一收口 formal / evidence 两路），`retrieval_rerank_enabled=True` + 非 mock provider 门控，尾部候选保持钉住；rerank 失败/超时/坏响应降级为 RRF 顺序（trace 记 `rerank_signal=degraded:*`），mock/disabled 保持融合顺序。settings 增 `retrieval_rerank_enabled`/`rerank_model`/`rerank_top_m`/`rerank_timeout_seconds`。单测 `tests/test_service_search_rerank.py` 用注入的确定性 provider 验证重排 / mock 跳过 / 降级 / disabled / top_m 边界五条路径；既有用例（mock 默认）顺序不变。
5. **PR-4 评测门禁（已完成）**：`tests/eval/`（dataset / providers / harness / test）+ `scripts/test.sh --suite eval` + CI 非阻塞 `eval-report` job（summary + artifact）；细节与首轮基线发现（CJK 分词修复）见 §10。剩余动作是运维项而非代码：网关就绪后以 `KNOWLEDGE_EVAL_PROVIDER=live` 跑一轮并归档，作为 v1.0 验收记录。

## 12. 风险

- **检索质量需真实评测才能确认达标**：故 §10 前置评测集；RRF 选型降低调参风险。
- **切模型维度地雷**：§5 换维需重建 Weaviate class + 全量再索引，不可就地混维——PR-2 必须把再索引与运维顺序做实，遗漏会静默返回坏结果。
- **新增 Weaviate 运维面**：v1.0 引入 Weaviate 服务（部署、健康、备份、class 生命周期）。§6 的向量后端降级保证抖动不致命，但运维基线必须覆盖 Weaviate（PR-2）。
- **rerank 默认开启的依赖**：强依赖 Router rerank 服务就绪；§6 的降级到 RRF 是硬保障，rerank 未就绪时整体仍可用。
- **范围膨胀**：评测自动化按阶段推进（先非阻塞报告），不阻塞 v1.0 主链路上线。
