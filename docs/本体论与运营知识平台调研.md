# 本体论与运营知识平台调研

> 调研日期：2026-10-23
>
> 目的：在 Knowledge 引入 DomainObject、Relation 和 Assertion 之前，确认市场上已有的相近产品、可借鉴的数据模型和适合当前项目的实现边界。

下一步进入实现前，先执行[运营本体 V1 构建风险评审](运营本体V1构建风险评审.md)中的无代码验证，确认“合同—产品—组织”关系确实解决当前检索无法稳定回答的真实决策问题。

需要从成功产品中选择具体机制时，参见[运营本体成功产品借鉴分析](运营本体成功产品借鉴分析.md)。该文档重点比较 Palantir、Wikibase、Reltio、Stardog 和 Neo4j，并明确 Knowledge 应借鉴与拒绝复制的边界。

## 1. 结论

Knowledge 需要补充的能力在市场上已经有成熟先例，但没有一个开源产品可以直接替代当前项目。

最接近的产品是 Palantir Foundry Ontology。它把对象、属性、关系、动作、函数、权限和应用组合成一个面向组织运营的语义层。它的核心价值不是“把数据放进图数据库”，而是让 AI、分析工具和业务应用对同一组业务对象做可控的查询和操作。

其他产品分别覆盖其中一部分：

- Stardog、TopQuadrant、PoolParty 重点解决企业语义建模、知识图谱、规则、数据质量和治理。
- Semarchy、Ataccama、Informatica 等 MDM 产品重点解决合同、产品、客户、员工等主数据的身份合并、黄金记录、层级和数据 steward 治理。
- Wikibase 重点解决实体、属性、陈述、限定条件、来源引用和协作版本。
- TypeDB 重点解决 schema-first 的实体、关系、属性和规则推理。
- TerminusDB 重点解决带版本控制的知识图谱、分支、合并、差异和时间旅行。
- OpenSPG/KAG、Microsoft GraphRAG 重点解决从非结构化内容构建图结构，以及图结构和文本检索的混合推理。

因此，Knowledge 应该采用组合路线：

```text
Warehouse 资产
  -> Evidence 证据
  -> DomainObject / Relation / Assertion
  -> Review / Revision / Release
  -> Grant / Policy
  -> Structured Query + Hybrid Retrieval
  -> Agent Action / Artifact
```

当前不建议直接引入 Neo4j、RDF 三元组平台或完整 Palantir 式运行时。Knowledge 已经具备 Evidence、Release、Grant 和 AgentRun 这些基础，应先在 PostgreSQL 中补充轻量的对象与事实模型，再根据真实查询和动作需求决定是否投影到专用图系统。

## 2. 先区分四个概念

| 概念 | 解决的问题 | Knowledge 中的对应关系 |
| --- | --- | --- |
| 本体论 Ontology | 世界中有哪些类型、属性、关系、约束和动作 | 待补充的类型与关系定义 |
| 知识图谱 Knowledge Graph | 这些类型和关系有哪些真实实例 | 待补充的 DomainObject、Relation |
| 事实/断言 Assertion | 某个对象在某个时间、来源下具有什么事实 | 待补充；必须绑定 Evidence |
| RAG | 从原始文本中找相关片段并生成回答 | 当前已有的 chunk、embedding、检索和 rerank |

本体不是把所有文档强行转换成图。可靠的系统应该同时保留原始文本、结构化对象和事实证据。结构化关系负责过滤、联结和计算，原始证据负责解释、引用和人工复核。

## 3. 产品分层

### 3.1 运营本体平台

#### Palantir Foundry Ontology

Palantir 官方将 Ontology 定义为组织的 operational layer，位于数据集、虚拟表和模型之上，把数字资产连接到真实世界的对象；其模型包含 objects、properties、links，以及 actions、functions 和动态安全。官方文档还提供对象类型、链接类型、动作类型、函数、接口、版本变更和对象安全等能力。

它解决的是：同一个客户、产品、设备或订单，如何被分析、应用、AI 和业务人员用同一套语义理解，并且可以执行受控动作。

对 Knowledge 的启发：

- 不能只建对象和关系，还要考虑发布、权限、动作和审计。
- `Action` 是本体的一部分，例如接受候选、发布版本、撤销授权、标记过期和启动分析。
- 本体必须连接真实数据源，不能成为脱离 Warehouse 的手工目录。

它不适合作为当前项目的直接依赖：闭源、系统范围大、部署和商业成本高，且其运行时边界与 YeYing 的 Chat、Agent、Warehouse 分工不同。

### 3.2 企业语义与知识图谱平台

| 产品 | 公开定位 | 可借鉴能力 | 对 Knowledge 的限制 |
| --- | --- | --- | --- |
| [Stardog](https://www.stardog.com/platform/) | 企业知识图谱和语义层 | RDF/OWL、SPARQL、SHACL 约束、推理、实体解析、虚拟图、跨源查询 | 更偏企业数据语义平台，业务动作、AgentRun 和 Warehouse app 边界需要自行建设 |
| [TopQuadrant TQ Data Foundation](https://www.topquadrant.com/tq-data-foundation) | 面向 AI 的受治理上下文层 | RDF/OWL/SHACL/SPARQL、版本历史、治理、连接器、AI 草拟模型和 Agent context | 商业平台；本体治理能力强，但不是 Knowledge 的发布授权和运行记录模型 |
| [PoolParty Semantic Suite](https://www.poolparty.biz/) | 企业知识图谱、分类法和语义 AI | taxonomy、ontology、文本挖掘、语义搜索和企业知识图谱 | 更偏语义资产和内容治理，Agent 动作与运行 provenance 需要另建 |
| [ServiceNow CSDM](https://www.servicenow.com/products/common-service-data-model.html) | IT 服务和配置项的标准化业务模型 | 领域对象、关系、服务依赖、运营流程和权限 | 是 ITSM 领域模型，不是通用知识库或通用本体平台 |

这些产品说明，企业本体的难点不只是抽取实体，还包括约束、来源、冲突、访问控制、变更管理和运营动作。

### 3.3 主数据管理 MDM

合同、产品、客户、员工这些对象也属于 MDM 的核心领域。MDM 通常从多个业务系统合并重复记录，解析“这些记录是不是同一个客户/产品/员工”，维护黄金记录、层级、数据质量、人工 steward 和审批工作流。

| 产品 | 公开定位 | 可借鉴能力 | 和 Knowledge 的边界 |
| --- | --- | --- | --- |
| [Semarchy Data Platform](https://semarchy.com/platform/) | MDM、DataOps、数据质量和受治理 AI 数据产品 | 多域建模、Golden Record、记录血缘、审批工作流、面向 Agent 的受控数据产品 | 面向企业主数据整合的商业平台；Knowledge 当前不应成为 HR/CRM/ERP 主数据的权威写入系统 |
| [Ataccama MDM](https://www.ataccama.com/platform/master-data-management) | 多域 MDM 和数据质量 | 记录匹配、去重、合并/拆分、Golden Record、数据 steward 和变更审批 | 更适合治理权威结构化业务记录，不能替代文档证据生产和 Knowledge Release |
| [Informatica MDM](https://www.informatica.com/products/master-data-management.html) | 企业多域主数据管理 | 客户、产品等实体统一、跨系统数据质量和治理 | 商业平台，实施通常涉及企业数据集成与主数据项目 |
| [Reltio](https://www.reltio.com/) | 云原生多域 MDM 和实体 360 | 实体解析、关系网络、跨域主记录和实时数据共享 | 商业 MDM 平台，目标是可靠的实体数据而非证据优先的文档知识治理 |

关键区别：**MDM 管理“这个客户/产品是谁，哪个记录是主记录”；Knowledge 管理“我们基于什么证据，知道关于它什么事实，这些事实何时有效、谁审核并发布了它”。**两者会共享 DomainObject 与标识映射，但不能互相冒充权威数据源。

### 3.4 可借鉴的开源模型和底座

| 项目 | 主要能力 | 对 Knowledge 的价值 | 注意事项 |
| --- | --- | --- | --- |
| [Wikibase](https://www.mediawiki.org/wiki/Wikibase) | Item、Property、Statement、Qualifier、Reference、Rank 和协作修订 | 最适合参考“一个事实如何带限定条件、来源和多个版本” | 它是协作知识图谱，不提供 Palantir 式业务动作和服务授权；软件、实例数据和内容许可需要分别核对 |
| [TypeDB](https://typedb.com/docs/core-concepts/typeql/entities-relations-attributes/) | schema-first 的 Entity、Relation、Attribute、规则和 TypeQL 查询 | 适合参考强类型关系模型、约束和规则推理 | 更像图数据库和推理引擎，不包含 Knowledge 的 Evidence/Release/AgentRun 产品层；服务端仓库标记为 MPL-2.0，商业版本需单独核对 |
| [TerminusDB](https://terminusdb.com/docs/) | 带版本控制的知识图谱、分支、合并、差异、时间旅行和 Datalog/WOQL | 适合参考知识版本、历史查询、分支和合并 | 需要自行建设服务身份、发布授权、证据审核和 Agent 运行模型；服务器仓库标记为 Apache-2.0 |
| [OpenSPG/KAG](https://github.com/OpenSPG/KAG) | Schema 约束的知识构建、逻辑形式引导推理、图与文本互索引 | 适合参考专业领域知识抽取、图推理和混合检索 | 更偏 AI 构建与问答框架，不是完整知识运营控制面；KAG 仓库标记为 Apache-2.0 |
| [Microsoft GraphRAG](https://github.com/microsoft/graphrag) | 从文档生成实体、关系、社区摘要并用于图增强检索 | 适合参考从非结构化文本生成候选图结构的流水线 | 是检索框架，不提供正式本体治理、事实审核、发布版本和动作权限；仓库标记为 MIT |
| [Neo4j](https://neo4j.com/) | 属性图数据库、图查询和 GraphRAG 生态 | 可作为高复杂关系查询的后端候选 | 它是基础设施，不等于本体产品；不能替代 Knowledge 的 Evidence、Release 和 Grant |

## 4. 与 Knowledge 的匹配度

| 能力 | Palantir | 语义平台 | Wikibase / TypeDB / TerminusDB | OpenSPG / GraphRAG | Knowledge 当前状态 |
| --- | --- | --- | --- | --- | --- |
| DomainObject 和类型 | 强 | 强 | 强 | 中 | 尚未建立 |
| 显式 Relation | 强 | 强 | 强 | 中-强 | 只有内部领域关系，缺少通用关系边 |
| 事实证据和引用 | 中 | 中-强 | 强 | 中 | Evidence 已有，是当前优势 |
| 时间、版本和发布 | 强 | 中-强 | 强 | 弱-中 | Revision/Release 已有，事实有效期仍需补 |
| 约束和冲突治理 | 强 | 强 | 中-强 | 中 | item contract 有基础，事实冲突未完成 |
| 动作和业务流程 | 强 | 中 | 弱 | 弱 | Release、Grant、AgentRun 已有，ActionType 未抽象 |
| Agent/RAG 接入 | 强 | 中-强 | 弱-中 | 强 | Service Search 和 AgentRun 已有 |
| 开源可自建 | 否 | 通常否 | 是/部分是 | 是 | Knowledge 可控，但根许可证仍需补齐 |

这张表的重点是：Knowledge 不需要在每个维度都追赶 Palantir。它应该保住已有的 Evidence、Release、Grant 和 AgentRun，再补齐对象、关系、断言和动作之间的连接。

| 目标对象/问题 | 更接近的产品类别 | 主要能力 |
| --- | --- | --- |
| 合同中的条款、义务、期限、证据和版本 | Knowledge + 语义平台 | 文档证据、事实断言、有效期、冲突审核和发布 |
| 产品主数据、SKU 去重、产品层级、跨系统产品编码 | MDM | 匹配、合并、主记录、层级和系统间分发 |
| 客户 360、同一客户跨 CRM/ERP/支持系统的识别 | MDM + 知识图谱 | 实体解析、身份合并、关系视图和数据质量 |
| 员工组织关系、岗位任职、授权和敏感属性 | HRIS/MDM + Policy | 权威 HR 主数据、任职有效期、组织层级、PII 权限 |
| “哪个员工在某时间代表哪个部门批准了哪份合同” | Knowledge + MDM/HRIS | DomainObject 联结、时间有效关系、审批证据与审计 |

Knowledge 可以连接这些对象、补充有证据的事实和提供可审计读取，但不应在没有明确业务授权时成为合同系统、PLM、CRM 或 HRIS 的权威主数据源。

## 5. 对 Knowledge 的具体设计建议

### 5.1 分成系统本体和业务本体

系统本体是 Knowledge 自己固定的类型：

```text
KnowledgeBase
Source
SourceAsset
EvidenceUnit
KnowledgeItem
KnowledgeItemRevision
KBRelease
ServicePrincipal
ServiceGrant
AgentRun
AgentRunArtifact
```

业务本体由每个知识库或领域扩展，例如：

```text
Contract
Product
Customer
Employee
Organization
Policy
Project
```

`KnowledgeItem` 是一条经过治理的知识陈述；`DomainObject` 是真实世界的对象；`Relation/Assertion` 是对象之间带时间、来源和状态的事实。三者不能合并成一个表或一个概念。

### 5.2 推荐的最小模型

```text
OntologyDefinition
OntologyVersion
ObjectType
DomainObject
RelationType
DomainRelation
Assertion
AssertionEvidenceLink
ActionType
```

关键约束：

- 对象拥有稳定的 `object_type`、`object_id` 和外部系统标识。
- 关系必须声明方向、两端类型、基数和是否允许反向查询。
- 断言必须支持 `valid_from`、`valid_to`、`observed_at`、`confidence` 和 `status`。
- 每条正式断言至少关联一个 Evidence；模型抽取结果先处于 `candidate` 或 `pending_review`。
- 冲突事实不能静默覆盖，应保留多个断言，并通过来源、时间、优先级和审核状态决定当前视图。
- Ontology、断言和 Release 都要有版本，查询必须能回答“当前事实”和“某个历史版本事实”。
- Grant 负责授权哪些对象、关系或 Release 可被服务读取；不能只在检索结果返回后再做权限过滤。

### 5.3 存储路线

第一阶段使用 PostgreSQL 足够：对象和关系使用普通表，扩展属性使用 JSONB，关系查询增加复合索引，事实与证据用显式关联表；向量仍由现有向量后端负责，原始文件仍在 Warehouse。

只有出现以下需求时，才考虑专用图后端：

- 关系深度超过 3 到 4 跳且查询成为主要负载；
- 需要复杂规则推理或 RDF/OWL 互操作；
- 多个外部系统需要共享同一套图查询协议；
- PostgreSQL 的递归查询、索引和审计模型已经成为瓶颈。

### 5.4 第一批验证场景

建议先验证“合同—产品—组织”关系，而不是一开始覆盖所有员工数据：

```text
Contract C123
  --SIGNED_BY--> Organization O1
  --APPLIES_TO--> Product P7
  --VALID_IN--> Region CN
  --SUPPORTED_BY--> Evidence E9
```

需要验证的问题：

1. 当前生效的产品合同是什么？
2. 某合同覆盖哪些产品和地区？
3. 合同内容发生变化后，哪些知识项和 Release 需要标记 stale？
4. Chat 服务是否有权读取该合同？
5. Agent 能否基于合同事实发起一个受控动作？

员工对象应在权限、PII、组织层级和离职状态模型明确后再接入，避免把人事数据当作普通文档处理。

## 6. 最终判断

Knowledge 适合走“轻量运营本体”路线：

```text
Evidence-first
+ Typed Domain Objects
+ Versioned Assertions
+ Release / Grant Governance
+ Agent Actions
```

它不应该变成通用的企业知识图谱数据库，也不应该把所有事实交给 LLM 自动写入。模型负责提出候选对象和断言，Evidence、约束、审核、版本和权限决定什么能成为正式知识。

Knowledge 当前最值得借鉴的对象是：

- Palantir：对象、关系、动作、权限和运营应用的整体闭环；
- Wikibase：断言、限定条件、来源引用和协作修订；
- Stardog/TopQuadrant：本体治理、约束和语义层；
- TypeDB：强类型关系和规则；
- TerminusDB：版本、分支、差异和历史；
- OpenSPG/KAG/GraphRAG：从非结构化内容构建候选图并进行混合推理。
